## 2026-08-15 「気をつける」だけでは同じ非効率パターンを繰り返した→実行時ガードを追加

**症状**: `scripts/backfill-d1-gap-to-r2.mjs`で踏んだ「月ごと・ページごとにR2マージ関数を
呼んでしまい、同じカードファイルを何度も書き直す」非効率パターンを、その日のうちに
`scripts/fix-illegal-prints-in-oracle-history.mjs`という別の新しいスクリプトで再び踏んだ。
インシデントログに書いて「次から気をつける」だけでは不十分だった。

**教訓**: 文書に記録するだけの再発防止策は、次にコードを書くときに自分がそれを思い出して
実際に参照する保証が無い限り機能しない。人間の注意力・記憶に頼る対策と、コード自体に
組み込む機械的な対策は別物で、後者の方が信頼できる。

**対応**: `scripts/lib/r2PriceArchive.mjs`の`mergeOraclePriceRows`/`mergePrintPriceRows`に
呼び出し回数カウンタを追加し、同一プロセス内で3回以上呼ばれたら例外を投げるようにした。
正当な日次スクリプトは1プロセスにつき1〜2回しか呼ばないため、ループ内で呼んでしまう
バグを実行してすぐに（30ヶ月分処理し終わってから気づくのではなく）機械的に検知できる。

## 2026-08-15 R2の請求サイクルはカレンダー月ではなくアカウント単位の契約日基準

**症状**: 今日1日でR2書き込みリクエストがどれだけ消費されたか、GraphQL Analytics APIで
`date_geq: "2026-08-01"`のようにカレンダー月の1日を起点にクエリして概算していたが、
実際の請求サイクルの起点はそれとは異なっていた（このアカウントは8/13起点）。

**教訓**: Cloudflareの利用量は「カレンダー月」ではなく「アカウントの請求サイクル」で
リセットされる（契約日に依存する）。月初を起点に見積もると実態とズレることがある。
正確な期間はCloudflareダッシュボードの「アカウント管理 > 請求 > 支払い請求可能な使用量」
で確認するのが確実（このページは請求データと同じ集計元を使っているため実際の請求と一致する）。

## 2026-08-15 TCGCSVバックフィル分に使用不可プリントが混入していた

**症状**: ユーザー指摘により、オラクル単位の「全プリント中最安値」に使用不可プリント
（`not_tournament_legal`、金縁/銀縁/memorabilia区分等）が含まれていることが発覚。
過去にも同じ指摘を受けていたはずだったが、再発していた。

**原因**: 日次の実データ用スクリプト（`compute-cheapest-price-snapshots.mjs`・
`snapshot-catalog-prices.mjs`）は正しく`not_tournament_legal`を除外していたが、
2024-02〜2026-07-24のTCGCSV一括バックフィル（`ml/fetch_tcgcsv_history.py`）はこのフィルタを
一切実装していなかった。「日次スクリプトで対応済みだから大丈夫」という思い込みで、
一括バックフィル側の実装を個別に確認していなかった。

**教訓**: 「同じ種類の処理を複数の場所（日次バッチ・一括バックフィル・手動スクリプト等）で
別々に実装している場合、ビジネスルール（除外条件、フィルタ等）は個別に確認する」。
1箇所直しても他の実装にコピーされていない/漏れていることがある。今回のケースでは
「使用不可プリントを除外する」がまさにそのルールで、複数箇所に散らばって実装されていた。

**対応（1回目、不十分だった）**: `scripts/fix-illegal-prints-in-oracle-history.mjs`（一時
スクリプト）で、プリント単位の月次バルクファイルから使用不可プリントを除外して最安値を
再計算し、正規版の代わりが見つかった日だけオラクル単位の価格履歴を上書きした。

**症状（再発）**: Black Lotus等の超高額・低流動性カードで、修正後も使用不可プリント
（Collectors' Edition）が最安値のまま残っていることが判明（ユーザー指摘）。

**原因（2回目）**: 1回目の修正は「使用不可を除外して再計算し、正規版の代わりが見つかった日
だけ上書きする」方式だった。しかしBlack Lotusのような取引頻度の低いカードは、TCGCSVに
その日データがあったのが使用不可プリントだけ、という日が多い。除外後に正規版の代わりが
1件も無いと「書き込み対象から漏れる」＝古い（使用不可プリント由来の）値がそのまま
残ってしまっていた。「除外して再計算」だけでは不十分で、「除外した結果、代わりが無い日は
明示的にnullで上書きする」まで含めないと、汚染されたデータを完全には除去できない。

**対応（2回目）**: `scripts/fix-illegal-only-dates.mjs`（一時スクリプト）で、使用不可も
含めた全プリントで最安値を計算し直し、「その日の最安が使用不可プリントだった」ケースだけを
特定。正規版の代わりがあればその値、無ければ明示的に`null`（価格データ無し扱い）で
上書きした（396,610件、687オラクル）。

**教訓**: 「不正なデータを除外する」修正をするときは、「除外した後に代わりのデータが
無いケース」を明示的に考慮する。「除外して再計算」だけだと、代わりが見つかった場合しか
上書きされず、代わりが無いケースは古い不正なデータが暗黙のうちに生き残る。

## 2026-08-15 継続注目カード（価格連続上昇）の判定方式を再設計（2段階）

**症状**: 使用不可プリント混入により、`compute-card-streaks.mjs`の連続上昇日数計算
（直近60日分をR2からスキャンし、配列の隣接要素同士を比較する方式）が汚染されたデータの
影響を受けていることが発覚。ユーザーから設計自体の見直しを提案された。

**旧方式（配列スキャン）の構造的な弱点**:
1. 配列の隣接要素（`series[i]` vs `series[i-1]`）を比較していたため、日付が1日でも欠けると
   実際には連続していない日同士を「連続」として誤集計する
2. 60日分のウィンドウが、データソースの品質が異なる複数の期間
   （TCGCSVバックフィル分と日次実データ分）を跨ぐことがあり、過去のデータ品質問題が
   直近の計算結果に影響する

**1回目の対応（不十分だった）**: `compute-trending-scores.mjs`と同じ「前日分の継続日数・
基準値を引き継ぎ、前日比プラスなら+1日、そうでなければリセット」方式に変更。ランキング用の
事前計算キャッシュ（`price-changes/latest.ndjson.gz`、直近7日分）を読むだけで完結するように
した。しかしこれも「前日のcard_streaksの値を信頼する」という意味では状態を持っており、
1日でも計算が飛べばそこから先ずっとズレを引きずるリスクが残っていた
（ユーザーから「カード自身の価格履歴を見れば分かるはず」と再度指摘を受けた）。

**2回目の対応（現在の設計）**: 前日の状態を一切参照しない完全ステートレス方式に変更。
日次バッチ（GitHub Actions、CPU時間制限なし）側で、月次バルクファイルから
`STREAK_LOOKBACK_DAYS`（30日）分を読み、暦日ベースで（配列のインデックスではなく、
実際の日付が1日前かどうかを見て）当日から遡ってその場で毎回計算し直す。ランキング用の
小さいキャッシュ（サイトが毎リクエストで読む、7日分に維持）とは完全に分離し、
「サイト側の読み込みを軽く保つ」と「streakの参照期間を十分取る」を両立させた。

**教訓**:
- 状態を引き継ぐ設計（前日の値を信頼する）は、引き継ぎが1回でも壊れると誤りが伝播し続ける。
  ソースデータから毎回計算し直せるなら、多少コストが増えてもステートレスな方が壊れにくい
- 「サイトが毎リクエストで読むキャッシュ」と「バッチが必要な分だけ読む参照データ」を
  同じファイルで兼用しようとすると、どちらかの都合（キャッシュは小さく、バッチは長期間欲しい）
  を犠牲にすることになる。用途が違うなら素直に分ける
- 同じプロジェクト内に、同種の問題（前日比の連続日数計算）に対する複数の異なる実装
  （`trending_scores`・`card_streaks`）が存在すると、弱い方の実装だけが後からバグを踏む。
  同じ種類の計算をする箇所が複数あるときは実装方針が割れていないか確認する

## 2026-08-14 Parquet+hyparquetによる本番CPU時間超過

**症状**: デッキ未使用カードの価格履歴をR2に追加した直後、検索・カード詳細ページなど無関係な
ルートまで含めて本番エラーになった。

**原因**: OpenNext（Cloudflare Workers向けNext.jsアダプター）は全ルートを1つのWorkerバンドルに
まとめる。R2読み取りに使ったhyparquet（Parquetパーサー）がバンドルに含まれた分だけ、
価格履歴を読まない無関係なルートまでコールドスタートコストが増え、Workers無料プランの
CPU時間制限（10ms/リクエスト）を超過した。動的importに変えても改善しなかった
（Workersはブラウザと違い実行時の追加チャンク取得ができず、結局同じバンドルに含まれる）。

**教訓**: 「重い依存ライブラリを追加する」変更は、そのライブラリを使わないルートにも
コストを及ぼす。Workers環境でCPU時間予算がシビアな場合、外部ライブラリ非依存の実装
（標準Web API等）を優先する。

**対応**: git revertで即座に復旧。恒久対応としてgzip圧縮NDJSON + Workers標準
`DecompressionStream`に置き換え、外部ライブラリへの依存を無くした。

## 2026-08-14 Cloudflare D1の日次リクエスト数上限超過

**症状**: 価格推移グラフ・ランキングページの表示のたびにD1（価格履歴アーカイブ用）へのクエリが
発生し、無料枠の読み取り上限（500万行/日）を大幅に超過（実測225M行/日）していた。

**原因**: D1は「容量」ではなく「日次の読み書き行数」が実質的な制約。当初「500MB容量制限」だと
誤認していたが、ユーザー提供のダッシュボード画面で発覚した。価格履歴のような無期限に伸びる
時系列データを、リクエストのたびに広い範囲クエリするテーブルには根本的に不向きだった。

**教訓**: D1のコスト特性を勘違いしたまま設計判断をした。無料枠の制約は思い込みでなく
公式ドキュメント（`developers.cloudflare.com/d1/platform/pricing`）で必ず確認する。

**対応**: 価格履歴アーカイブをD1からリクエスト回数課金のR2へ全面移行。

## 2026-08-14〜15 R2移行に伴う多重の設計ミス

一度の移行作業で複数の設計ミスを重ねて発覚した。まとめて記録する。

1. **月次バルクファイルを毎回全部読む設計だった** → 1カード分の履歴を見るだけなのに
   30ヶ月分（各5〜8MB圧縮）を毎回読んでいた。Parquet事故と同種のCPU時間超過リスク。
   → カード単位ファイル（1カード=1ファイル）に再設計。

2. **D1→R2移行時、移行直前の期間をコピーし忘れた** → TCGCSVバックフィルは意図的に
   「2026-07-25以降はD1に実データがあるので触らない」設計だったが、そのD1データを
   R2へ移す作業自体を忘れた。カード詳細ページで直近3週間分の価格が欠落した
   （ユーザー報告で発覚）。
   → D1に残っていた674,570行＋1,201,109行をR2へバックフィル。

3. **バックフィルスクリプトが同じカードファイルを14回も書き直していた** → D1から
   50,000行ずつページングして取得するたびにR2マージ関数を呼んでいたため、1ページ
   （≒1.5日分）ごとにほぼ全カードのファイルへGET+PUTが発生し、本来1回で済む処理が
   ページ数分（約14回）繰り返されていた。2時間半で15%しか進まなかった。
   → 全ページを読み切ってから1回だけマージする方式に変更。

**教訓**: 1つの機能追加で「読み込み設計」「移行漏れ」「バックフィルの効率」という
異なる種類のミスが同時多発した。範囲が広い変更ほど、個々のステップを分けて検証する。

## 2026-08-15 ランキングページが11〜37秒かかっていた（原因が2つあった）

**症状**: R2への移行後、`/rankings/[format]`の表示が11〜37秒かかるようになった。

**原因1**: `dbCardRanking.ts`が価格変化率を求めるのに、オラクル約100件それぞれに対して
個別のR2 GetObjectを送っていた。1件あたりは速くても、100件分のネットワーク往復
（TTFB）が直列に積み重なった。D1時代は`IN (...)`で1クエリにまとめられていたが、
R2はオブジェクト単位でしかリクエストできない。
→ 全オラクル分の「直近価格＋3日前比変化率」を1ファイルにまとめた事前計算キャッシュ
（`price-changes/latest.ndjson.gz`）を追加し、1回のGetObjectで済むようにした。

**原因2（1を直した後も残っていた）**: `getBestCardImages`が内部で呼ぶ
`getLatestPricesForPrints`のR2フォールバックが、欠損プリント1件ごとに個別GetObjectを
送る設計だった。カード詳細ページ（数件規模）では問題にならないが、ランキングページ
（100カード分の全プリントをまとめて問い合わせる）だと数百件規模のリクエストが発生していた。
→ 欠損件数が少ない（30件以下）場合だけR2フォールバックを試すよう上限を追加。

**教訓**: 「N件のリストページで、1件用に設計された関数を使い回す」と、その関数の中に
隠れたN+1（またはそれ以上の）リクエストパターンが埋まっていないか要確認。1つ直しても
別の場所に同種の問題が潜んでいることがある。

## 2026-08-15 gzipSync/gunzipSyncが並列処理を無効化していた

**症状**: R2のD1ギャップ移行バックフィル（ThreadPoolExecutor相当の16並列のはずが)、
2時間半で15%しか進まなかった。並列化しているはずなのに速度が全く出ていなかった。

**原因**: `scripts/lib/r2PriceArchive.mjs`がgzip圧縮・展開に同期版
（`gzipSync`/`gunzipSync`）を使っていた。Node.jsはシングルスレッドのイベントループで
動くため、同期処理は実行中ずっとプロセス全体を止める。「16並列」で呼んでいたつもりでも、
どれか1つが同期gzip処理に入るたびに他の15個も含めて全部停止していた。

**教訓**: Node.jsで「並列化した」と思ったら、その中に同期API（`*Sync`関数）が
紛れ込んでいないか確認する。ネットワークI/Oは非同期でも、CPU処理（圧縮・展開等）が
同期のままだと並列化の効果が実質ゼロになる。

**対応**: `gzip`/`gunzip`の非同期版（`util.promisify`でPromise化）に変更。
`UV_THREADPOOL_SIZE`も引き上げてlibuvのスレッドプールを並列数に見合う数にした。

**再発防止の運用ルール**: 並列化を謳うスクリプトを実行する前にコードを確認し、
実行を始めたら一定時間後に進捗（rows/files per minute等）を実測して想定と大きく
乖離していないか必ずチェックする（「動いているから待つ」で済ませない）。

## 2026-08-15 12個のコミットを一度もpushしていなかった

**症状**: ローカルでR2移行のコード変更・コミットを済ませ、`npm run deploy`で本番Workerには
反映したが、GitHub Actionsの daily-data-pipeline が本番と異なる（移行前の）古いコードで
動き続け、大量のエラーを出していた。

**原因**: `npm run deploy`はローカルのビルド成果物を直接Cloudflareへアップロードするだけで、
GitHubリポジトリ（`origin`）は更新しない。GitHub Actionsは`origin`上のコードでしか動かない
ため、コミットしただけで満足し`git push`を忘れると、本番Workerとリポジトリ（＝CI）の
コードが乖離したまま気づかれない。

**教訓**: 「デプロイした」＝「pushした」ではない。特にCI（GitHub Actions）で動く
スクリプトに変更を入れた場合、`npm run deploy`だけでなく`git push`もセットで行う。
作業の節目でも`git status`（ahead/behindの表示）を確認する。

## 2026-08-15 R2書き込みコスト削減の差分チェックが、Supabaseとの比較で壊れた

**症状**: 継続注目カード（`card_streaks`、価格カテゴリ）が0件になった。トップページの
「価格上昇が続いているカード」欄が表示されなくなった。

**原因**: R2書き込み（無料枠100万件/月）を節約するため、「前日から値が変わったオラクル/
プリントだけをR2へ書く」差分ロジックを`card_current_prices`/`card_print_current_prices`
（Supabase、「今の価格」キャッシュ）との比較で実装していた。しかしこのSupabaseテーブルは
R2への書き込みが成功したかとは無関係に、日次バッチが実行されるたびに無条件で上書きされる。
同じ日にスクリプトを複数回実行した（デバッグ・検証のため）ことで、1回目の実行時点で
Supabase側が「今日の値」に更新され、その後R2側には一度も今日の日付の行が書き込まれない
まま「変化なし」と誤判定され続けた。`compute-card-streaks.mjs`は「最新の行が今日の日付で
なければそのオラクルをストリーク計算から除外する」ため、静かに0件になっていた。

**教訓**: 「Aが成功したかどうか」を、Aと無関係な理由でも更新されうるBの状態で判定しては
いけない。差分書き込みの「前回の値」は、書き込み先（R2）自身から読むか、書き込みと
アトミックに同期する何かでなければ信頼できない。この教訓は上記「gzipSync」の件と対になる：
一方は「並列化したつもりが同期処理が混入」、こちらは「差分チェックしたつもりが
信頼できない比較対象を使っていた」——どちらも"意図通りに動いているつもり"を実際の挙動で
検証しなかったことが共通の原因。

**対応**: Supabaseとの事前比較を削除し、全件をR2側のマージ処理へ渡す。実際に書き込むかどうかの
判定は`mergeCardFile`内で、書き込み先のR2ファイル自体と比較して行う（読み取りは無料枠に
余裕があるため、差分判定のためのGET自体は問題にならない）。
