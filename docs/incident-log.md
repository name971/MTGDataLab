# 障害・バグ記録

同じ種類のミスを繰り返さないための記録。何か新しく直したときはここに追記する。
コードを書く前、特に価格アーカイブ（R2/D1/Supabase）・日次バッチ・Cloudflare Workers周りを
触るときは、関連する過去の記録が無いか目を通すこと。

**記録するときの必須フェーズ**: 症状・原因・教訓を書いたら、必ず最後に
「これをシステム（コード）に組み込んで機械的に防げないか」を検討するフェーズを入れる。
検討した結果、組み込める場合は実際に実装して「対応」に書く。組み込めない/やらない場合も、
「なぜ組み込まなかったか」を明記する（検討せずに文章の教訓だけで終わらせない）。
文章に書くだけの再発防止策は次に活かされる保証が無いことが2026-08-15・08-17と
複数回実証済みのため（本ファイル該当箇所参照）。

## 2026-08-20 新Supabaseプロジェクトへの移行で`backfill-set-icons.mjs`の実行が漏れ、
全セットのアイコン画像が出ない状態のまま気づかず本番運用していた

**症状**: ユーザーから「Store Championshipsとかのプロモ系セットマークがScryfallから
ちゃんと取得できていない」と指摘。調べると対象はプロモに限らず`sets`テーブル650件
**全件**で`icon_svg_uri`がnullだった。`src/components/CardHero.tsx`は
`iconUrlBySetCode[setCode] ?? https://svgs.scryfall.io/sets/<code>.svg`という
命名規則フォールバックを持っているため、主要セットは偶然表示され気づきにくく、
命名規則が成り立たない一部セット（プロモ、Secret Lair Drop等）だけ壊れて見えた。

**原因**: 今回の新規Supabaseプロジェクト移行（本ファイルの一連の障害対応の一環）で、
カード/セット/価格などの基礎データは`import-full-catalog-local.mjs`経由で移したが、
`scripts/backfill-set-icons.mjs`（Scryfall `/sets`から`icon_svg_uri`を別途取得する
専用スクリプト）を実行し忘れていた。移行手順のチェックリストに独立したスクリプトとして
明記されておらず、「カタログを入れれば終わり」という思い込みで見落とした。

**教訓**: `import-full-catalog*.mjs`だけでは埋まらない、独立した`backfill-*.mjs`
スクリプト（set icon以外にも同種のものがあれば注意）がこのリポジトリには存在する。
DBを作り直す/移行するたびに、`scripts/backfill-*.mjs`を全部洗い出して実行漏れが
無いか確認する必要がある。命名規則フォールバックのような「無くても大体動いて見える」
救済コードは、根本原因（データ未投入）に気づくのを遅らせる副作用があることも留意。

**対応**: `node scripts/backfill-set-icons.mjs`を実行し650件全て復旧（未設定0件を確認）。
機械的な防止策としては、`scripts/check-data-health.mjs`（既存の日次ヘルスチェック）に
「`sets`テーブルで`icon_svg_uri IS NULL`の行数が一定割合を超えたら警告」のチェックを
追加するのが有効そうだが、今回は未実装（次にこの種の移行漏れを踏んだ時、または
`check-data-health.mjs`を触る機会に追加する）。

## 2026-08-22 MLランキング自動更新がFileNotFoundErrorで毎回失敗していたのに気づけなかった

**症状**: ユーザーから「注目カードランキングが更新されていない」と指摘。日次パイプラインの
「Predict and publish ML card ranking」ステップはログ上`success`扱いだったが、
`card_price_predictions`の最新`calculated_at`は8/15のまま何日も更新されていなかった。

**原因**: `ml/predict_and_publish.py`は`ml/data/price_history.parquet`・`static_attrs.parquet`
を直接ファイルから読むが、これらを生成する`ml/fetch_data.py`をワークフローに追加し忘れていた
（2026-08-21、採用率アーカイブ永続化のステップを追加した際、`usage_stats.parquet`を作る
`ml/build_usage_history_from_tournaments.py`は追加したのに、価格履歴・静的属性を作る
`ml/fetch_data.py`本体を呼ぶステップを入れ忘れた）。GitHub Actionsの毎回まっさらな
ランナーにはこれらのファイルが存在せず、`FileNotFoundError`で即座に失敗していたが、
このステップに`continue-on-error: true`を付けていたため、ジョブ全体は`success`のまま
何日も気づけなかった。

**教訓**: `continue-on-error: true`は「1ステップの失敗で他を止めない」ためのものだが、
「ステップが実は必ず失敗し続けている」ことを隠す副作用がある。新しいステップを
ワークフローに追加する際は、そのスクリプトが実際に依存する入力ファイル・前提データを
全部洗い出し、生成元のステップが本当に含まれているか確認する必要がある
（[[feedback_db_migration_checklist]]と同種の「見落としがちな依存関係の洗い出し漏れ」）。

**対応**: `Fetch base training data (price history, static attrs)`ステップ
（`python ml/fetch_data.py`）を追加。あわせて`scripts/check-data-health.mjs`に
「`card_price_predictions`の最新`calculated_at`が1日以上古い」ことを検知するチェックを
追加し、同種の「continue-on-errorで隠れた失敗」を次回は日次で機械的に検知できるようにした。

## 2026-08-21 TCGCSVバックフィルで使用不可版プリントの絞り込み漏れが再発（既知の不具合の再発）

**症状**: ユーザーから「古えの墳墓の価格グラフに使用不可のカードが入っている」と指摘。
以前（過去セッション、コミット`4c17b41`）に一度修正した「正規版データが無い日は
使用不可版（Collectors' Edition等）の価格が代わりに残ってしまう」バグと同じ症状。

**原因**: `4c17b41`の修正は本番の日次パイプライン（`scripts/snapshot-print-prices.mjs`等）
側にしか入っておらず、今回のSupabase障害復旧で新規に使った`ml/fetch_tcgcsv_history.py`
（過去データをTCGCSVから直接取得するスクリプト）の`build_candidate_scryfall_to_oracle()`
には同じ`not_tournament_legal=false`の絞り込みが入っていなかった。「同じ種類の不具合の
修正」が、修正対象のロジックが複数箇所（本番パイプラインとバックフィルスクリプト）に
重複して存在することを見落とし、片方にしか適用されていなかった。

**教訓**: 「使用不可版を除外する」のような正しさに関わるフィルタ条件は、同じ目的の
処理が複数のスクリプトに分散している場合、修正時に全箇所を洗い出す必要がある。
今回のケースでは、日次パイプラインとバックフィルスクリプトが同じ
`card_prints`→`scryfall_id`→`oracle_id`の対応表を独立に構築しており、片方だけ直しても
気づけなかった。

**対応**: `ml/fetch_tcgcsv_history.py`の`card_prints`取得クエリに
`&not_tournament_legal=eq.false`を追加し、8/17-20分を正しいデータで再取得した。
機械的な防止策としては、`card_prints`から`scryfall_id→oracle_id`対応表を作る処理を
共通関数化し全スクリプトで使い回すのが理想だが、Python（ml/）とNode.js（scripts/）の
言語が分かれているため単純な関数共有はできない。次に同種の絞り込み漏れを踏んだら、
両言語で同じロジックのテストデータ（既知の使用不可版プリントのoracle_idを1件）を
使った簡易チェックスクリプトの追加を検討する（今回は未実装）。

## 2026-08-20 Workers KVのdelete操作日次上限(無料枠1000件/日)を確認せず4443件削除し、当日分を使い切った

**症状**: ISRキャッシュ反映のためWorkers KVのキー一括削除を2回実施（4319件→再デプロイ後に124件、
計4443件）。直後にダッシュボードで「KVリクエストが一時的にブロックされています」
「1日のdelete操作上限1000件を超過、2026-08-21 00:00 UTCにリセット」と表示された。

**原因**: [[feedback_check_supabase_capacity_before_bulk_ops]]で得た教訓（大量読み書きの前に
容量・残量を確認する）をSupabase以外のサービス（Cloudflare Workers KV）には適用していなかった。
「キャッシュは再生成可能だから消しても安全」という判断は正しかったが、削除件数そのものが
サービス側のレート制限に抵触するかどうかは別軸のチェックが必要で、それを怠った。

**教訓**: 「壊れても再生成できるから安全」と「操作回数がプラットフォームの無料枠上限に
収まるか」は別の確認事項。Cloudflare関連の操作（KV/D1/R2/Workers Scripts）は、
書き込み系だけでなく削除系にも無料枠の日次上限があることを前提に、事前に対象件数を数え、
必要なら分割・翌日以降に回すか判断する。4000件超の一括操作をする前に、まず対象件数を
確認してから実行するかどうかその場で立ち止まる。

**対応**: 今回は実害が軽微（既に必要な反映は完了済み）だったため、コード側のガードは
追加しない。次にKV等Cloudflareリソースへの大量delete/write操作を行う際は、実行前に
「件数 × 無料枠の日次上限」を必ず言葉に出して確認してから実行する運用とする
（[[feedback_think_before_acting_on_risky_ops]]参照）。

## 2026-08-20 新Supabaseプロジェクト移行で`db/search-design.sql`（検索RPC）の適用が丸ごと漏れていた

**症状**: ユーザーから「Black Lotusのページが無い」と報告。実際にはページ自体（`/cards/{oracleId}`）は
存在し200 OKだったが、サイト内検索（`/api/search-suggest`）で"Black Lotus"を検索しても
無関係な"Black Lotus Lounge"しかヒットしなかった。

**原因**: `src/lib/searchCards.ts`が呼ぶ`search_cards` RPC、`src/lib/nameMatching.ts`が
呼ぶ`resolve_oracle_id` RPC（トーナメント結果のカード名寄せにも使う）が、どちらも
新Supabaseプロジェクトに一度も作成されていなかった（`db/search-design.sql`を適用し忘れ）。
RPC呼び出しはエラーを握りつぶして空配列にフォールバックする設計のため、検索が
「0件」ではなく「一部だけヒットする（D1カタログ側の別経路のみ生きている）」という
中途半端な状態になり、機能停止に気づきにくかった。

これは[[project_scriptmigration_gaps]]（set-icon backfill漏れ、card_prints日本語画像
backfill漏れ）と同じパターンの3件目: `import-full-catalog*.mjs`で運ぶデータ以外に、
このリポジトリには独立して適用が必要なSQLファイル・スクリプトが複数存在し、
移行時にそれらを網羅的に洗い出せていなかった。

**教訓**: DBを作り直す/移行する際は、`db/schema.sql`だけでなく`db/*.sql`配下の
全ファイル、および`scripts/backfill-*.mjs`を機械的に列挙してチェックリスト化すべき。
「主要な機能を触ってみて動くか確認する」という受動的な確認では、検索のように
「エラーを握りつぶして一部だけ動いているように見える」機能の欠落を見逃す。

**対応**: `psql`で`db/search-design.sql`を直接適用し復旧（CREATE EXTENSION pg_trgm、
関連インデックス6件、`search_cards`/`resolve_oracle_id`関数）。次にDB移行する機会が
あれば、`db/`配下のSQLファイル一覧と`scripts/backfill-*.mjs`一覧を先に洗い出してから
着手する運用とする（今回は未実装、次回移行時に着手）。

## 2026-08-20 useSearchParams()未対応でprerenderが失敗、TOPページのMLランキングが本番に反映されなかった

**症状**: Supabaseプロジェクト移行後、`card_price_predictions`にデータを投入し、
`getMlRankingFromDb`が単体テスト（実ファイルでtop-level await、isolated）では正しく
100件返すことを確認したのに、`npm run deploy`を2回実行しても本番のTOPページに
「注目カードランキング」セクションが出なかった。KVの永続ISRキャッシュを4319件全削除しても
変化なし、`wrangler tail`で実リクエストを確認してもワーカー自体は`Ok`で応答していた。

**原因**: `src/components/MlRankingList.tsx`が`useSearchParams()`を使うクライアント
コンポーネントで、`src/app/page.tsx`側で`<Suspense>`に包まずに直接レンダリングしていた。
このページは`revalidate = 3600`でstatic prerenderの対象になるため、`next build`が
「useSearchParams() should be wrapped in a suspense boundary」で`/`ページのprerenderに
失敗し、`Export encountered an error on /page: /, exiting the build`でビルド全体が
非ゼロ終了していた。`package.json`の`deploy`スクリプトは
`opennextjs-cloudflare build && opennextjs-cloudflare deploy`で`&&`結合のため、
本来ビルド失敗時はデプロイされないはずだった。実際、直近の失敗した`npm run deploy`実行では
`wrangler deploy`まで到達せずエラー終了しており「デプロイに見えて実は古いバンドルが
そのまま使われていた」ケースは今回確認した限りでは無かった——つまり複数回試した
「デプロイ」自体がこの日はビルド失敗で止まっていた可能性が高い（正常時のログにだけ出る
"Populating remote KV incremental cache..."の行が、疑わしかった回のログに無かった）。

**教訓**: `npm run deploy`のログの最後だけ（"Uploaded mtgdatalab"等）を見て成功と
判断せず、ビルド段階の出力（"Populating remote KV incremental cache..."が出ているか）
まで確認する。バックエンドのデータ層が単体で正しく動くことを確認しても、それが
本番ページに反映される保証にはならない——prerender/ビルド自体の成否を別途確認する必要がある。

**対応**: `MlRankingList`を`<Suspense fallback={null}>`で包んでprerender失敗を解消
（[src/app/page.tsx](../src/app/page.tsx)）。デプロイスクリプト自体は`&&`で既に
ビルド失敗時にデプロイをスキップする作りだったため、追加のガードコードは不要と判断。
今後クライアントコンポーネントでフックを使う場合、それがstatic prerender対象の
ページから直接（Suspenseなしで）呼ばれていないか、`npm run deploy`のログで
ビルド完了の兆候を都度確認する運用とする。

## 2026-08-15 TCGCSVバックフィル分に使用不可プリントが混入していた

**症状**: ユーザー指摘により、オラクル単位の「全プリント中最安値」に使用不可プリント
（`not_tournament_legal`、金縁/銀縁/memorabilia区分等）が含まれていることが発覚。
過去にも同じ指摘を受けていたはずだったが、再発していた。

**原因**: 日次の実データ用スクリプト（`compute-cheapest-price-snapshots.mjs`・
`snapshot-catalog-prices.mjs`）は正しく`not_tournament_legal`を除外していたが、
2024-02〜2026-07-24のTCGCSV一括バックフィル（`ml/fetch_tcgcsv_history.py`）はこのフィルタを
一切実装していなかった。「日次スクリプトで対応済みだから大丈夫」という思い込みで、
一括バックフィル側の実装を個別に確認していなかった。

**教訓**: 「同じ種類の処理を複数の場所（日次バッチ・一括バックフィル・手動スクリプト等）で
別々に実装している場合、ビジネスルール（除外条件、フィルタ等）は個別に確認する」。
1箇所直しても他の実装にコピーされていない/漏れていることがある。今回のケースでは
「使用不可プリントを除外する」がまさにそのルールで、複数箇所に散らばって実装されていた。

**対応（1回目、不十分だった）**: `scripts/fix-illegal-prints-in-oracle-history.mjs`（一時
スクリプト）で、プリント単位の月次バルクファイルから使用不可プリントを除外して最安値を
再計算し、正規版の代わりが見つかった日だけオラクル単位の価格履歴を上書きした。

**症状（再発）**: Black Lotus等の超高額・低流動性カードで、修正後も使用不可プリント
（Collectors' Edition）が最安値のまま残っていることが判明（ユーザー指摘）。

**原因（2回目）**: 1回目の修正は「使用不可を除外して再計算し、正規版の代わりが見つかった日
だけ上書きする」方式だった。しかしBlack Lotusのような取引頻度の低いカードは、TCGCSVに
その日データがあったのが使用不可プリントだけ、という日が多い。除外後に正規版の代わりが
1件も無いと「書き込み対象から漏れる」＝古い（使用不可プリント由来の）値がそのまま
残ってしまっていた。「除外して再計算」だけでは不十分で、「除外した結果、代わりが無い日は
明示的にnullで上書きする」まで含めないと、汚染されたデータを完全には除去できない。

**対応（2回目）**: `scripts/fix-illegal-only-dates.mjs`（一時スクリプト）で、使用不可も
含めた全プリントで最安値を計算し直し、「その日の最安が使用不可プリントだった」ケースだけを
特定。正規版の代わりがあればその値、無ければ明示的に`null`（価格データ無し扱い）で
上書きした（396,610件、687オラクル）。

**教訓**: 「不正なデータを除外する」修正をするときは、「除外した後に代わりのデータが
無いケース」を明示的に考慮する。「除外して再計算」だけだと、代わりが見つかった場合しか
上書きされず、代わりが無いケースは古い不正なデータが暗黙のうちに生き残る。

## 2026-08-15 継続注目カード（価格連続上昇）の判定方式を再設計（2段階）

**症状**: 使用不可プリント混入により、`compute-card-streaks.mjs`の連続上昇日数計算
（直近60日分をR2からスキャンし、配列の隣接要素同士を比較する方式）が汚染されたデータの
影響を受けていることが発覚。ユーザーから設計自体の見直しを提案された。

**旧方式（配列スキャン）の構造的な弱点**:
1. 配列の隣接要素（`series[i]` vs `series[i-1]`）を比較していたため、日付が1日でも欠けると
   実際には連続していない日同士を「連続」として誤集計する
2. 60日分のウィンドウが、データソースの品質が異なる複数の期間
   （TCGCSVバックフィル分と日次実データ分）を跨ぐことがあり、過去のデータ品質問題が
   直近の計算結果に影響する

**1回目の対応（不十分だった）**: `compute-trending-scores.mjs`と同じ「前日分の継続日数・
基準値を引き継ぎ、前日比プラスなら+1日、そうでなければリセット」方式に変更。ランキング用の
事前計算キャッシュ（`price-changes/latest.ndjson.gz`、直近7日分）を読むだけで完結するように
した。しかしこれも「前日のcard_streaksの値を信頼する」という意味では状態を持っており、
1日でも計算が飛べばそこから先ずっとズレを引きずるリスクが残っていた
（ユーザーから「カード自身の価格履歴を見れば分かるはず」と再度指摘を受けた）。

**2回目の対応（現在の設計）**: 前日の状態を一切参照しない完全ステートレス方式に変更。
日次バッチ（GitHub Actions、CPU時間制限なし）側で、月次バルクファイルから
`STREAK_LOOKBACK_DAYS`（30日）分を読み、暦日ベースで（配列のインデックスではなく、
実際の日付が1日前かどうかを見て）当日から遡ってその場で毎回計算し直す。ランキング用の
小さいキャッシュ（サイトが毎リクエストで読む、7日分に維持）とは完全に分離し、
「サイト側の読み込みを軽く保つ」と「streakの参照期間を十分取る」を両立させた。

**教訓**:
- 状態を引き継ぐ設計（前日の値を信頼する）は、引き継ぎが1回でも壊れると誤りが伝播し続ける。
  ソースデータから毎回計算し直せるなら、多少コストが増えてもステートレスな方が壊れにくい
- 「サイトが毎リクエストで読むキャッシュ」と「バッチが必要な分だけ読む参照データ」を
  同じファイルで兼用しようとすると、どちらかの都合（キャッシュは小さく、バッチは長期間欲しい）
  を犠牲にすることになる。用途が違うなら素直に分ける
- 同じプロジェクト内に、同種の問題（前日比の連続日数計算）に対する複数の異なる実装
  （`trending_scores`・`card_streaks`）が存在すると、弱い方の実装だけが後からバグを踏む。
  同じ種類の計算をする箇所が複数あるときは実装方針が割れていないか確認する

## 2026-08-14 Parquet+hyparquetによる本番CPU時間超過

**症状**: デッキ未使用カードの価格履歴をR2に追加した直後、検索・カード詳細ページなど無関係な
ルートまで含めて本番エラーになった。

**原因**: OpenNext（Cloudflare Workers向けNext.jsアダプター）は全ルートを1つのWorkerバンドルに
まとめる。R2読み取りに使ったhyparquet（Parquetパーサー）がバンドルに含まれた分だけ、
価格履歴を読まない無関係なルートまでコールドスタートコストが増え、Workers無料プランの
CPU時間制限（10ms/リクエスト）を超過した。動的importに変えても改善しなかった
（Workersはブラウザと違い実行時の追加チャンク取得ができず、結局同じバンドルに含まれる）。

**教訓**: 「重い依存ライブラリを追加する」変更は、そのライブラリを使わないルートにも
コストを及ぼす。Workers環境でCPU時間予算がシビアな場合、外部ライブラリ非依存の実装
（標準Web API等）を優先する。

**対応**: git revertで即座に復旧。恒久対応としてgzip圧縮NDJSON + Workers標準
`DecompressionStream`に置き換え、外部ライブラリへの依存を無くした。

## 2026-08-14 Cloudflare D1の日次リクエスト数上限超過

**症状**: 価格推移グラフ・ランキングページの表示のたびにD1（価格履歴アーカイブ用）へのクエリが

**教訓**: D1のコスト特性を勘違いしたまま設計判断をした。無料枠の制約は思い込みでなく
公式ドキュメント（`developers.cloudflare.com/d1/platform/pricing`）で必ず確認する。

**対応**: 価格履歴アーカイブをD1からリクエスト回数課金のR2へ全面移行。

## 2026-08-14〜15 R2移行に伴う多重の設計ミス

一度の移行作業で複数の設計ミスを重ねて発覚した。まとめて記録する。

1. **月次バルクファイルを毎回全部読む設計だった** → 1カード分の履歴を見るだけなのに
   30ヶ月分（各5〜8MB圧縮）を毎回読んでいた。Parquet事故と同種のCPU時間超過リスク。
   → カード単位ファイル（1カード=1ファイル）に再設計。

2. **D1→R2移行時、移行直前の期間をコピーし忘れた** → TCGCSVバックフィルは意図的に
   「2026-07-25以降はD1に実データがあるので触らない」設計だったが、そのD1データを
   R2へ移す作業自体を忘れた。カード詳細ページで直近3週間分の価格が欠落した
   （ユーザー報告で発覚）。
   → D1に残っていた674,570行＋1,201,109行をR2へバックフィル。

3. **バックフィルスクリプトが同じカードファイルを14回も書き直していた** → D1から
   50,000行ずつページングして取得するたびにR2マージ関数を呼んでいたため、1ページ
   （≒1.5日分）ごとにほぼ全カードのファイルへGET+PUTが発生し、本来1回で済む処理が
   ページ数分（約14回）繰り返されていた。2時間半で15%しか進まなかった。
   → 全ページを読み切ってから1回だけマージする方式に変更。

**教訓**: 1つの機能追加で「読み込み設計」「移行漏れ」「バックフィルの効率」という
異なる種類のミスが同時多発した。範囲が広い変更ほど、個々のステップを分けて検証する。

## 2026-08-15 ランキングページが11〜37秒かかっていた（原因が2つあった）

**症状**: R2への移行後、`/rankings/[format]`の表示が11〜37秒かかるようになった。

**原因1**: `dbCardRanking.ts`が価格変化率を求めるのに、オラクル約100件それぞれに対して
個別のR2 GetObjectを送っていた。1件あたりは速くても、100件分のネットワーク往復
（TTFB）が直列に積み重なった。D1時代は`IN (...)`で1クエリにまとめられていたが、
R2はオブジェクト単位でしかリクエストできない。
→ 全オラクル分の「直近価格＋3日前比変化率」を1ファイルにまとめた事前計算キャッシュ
（`price-changes/latest.ndjson.gz`）を追加し、1回のGetObjectで済むようにした。

**原因2（1を直した後も残っていた）**: `getBestCardImages`が内部で呼ぶ
`getLatestPricesForPrints`のR2フォールバックが、欠損プリント1件ごとに個別GetObjectを
送る設計だった。カード詳細ページ（数件規模）では問題にならないが、ランキングページ
（100カード分の全プリントをまとめて問い合わせる）だと数百件規模のリクエストが発生していた。
→ 欠損件数が少ない（30件以下）場合だけR2フォールバックを試すよう上限を追加。

**教訓**: 「N件のリストページで、1件用に設計された関数を使い回す」と、その関数の中に
隠れたN+1（またはそれ以上の）リクエストパターンが埋まっていないか要確認。1つ直しても
別の場所に同種の問題が潜んでいることがある。

## 2026-08-15 gzipSync/gunzipSyncが並列処理を無効化していた

**症状**: R2のD1ギャップ移行バックフィル（ThreadPoolExecutor相当の16並列のはずが)、
2時間半で15%しか進まなかった。並列化しているはずなのに速度が全く出ていなかった。

**原因**: `scripts/lib/r2PriceArchive.mjs`がgzip圧縮・展開に同期版
（`gzipSync`/`gunzipSync`）を使っていた。Node.jsはシングルスレッドのイベントループで
動くため、同期処理は実行中ずっとプロセス全体を止める。「16並列」で呼んでいたつもりでも、
どれか1つが同期gzip処理に入るたびに他の15個も含めて全部停止していた。

**教訓**: Node.jsで「並列化した」と思ったら、その中に同期API（`*Sync`関数）が
紛れ込んでいないか確認する。ネットワークI/Oは非同期でも、CPU処理（圧縮・展開等）が
同期のままだと並列化の効果が実質ゼロになる。

**対応**: `gzip`/`gunzip`の非同期版（`util.promisify`でPromise化）に変更。
`UV_THREADPOOL_SIZE`も引き上げてlibuvのスレッドプールを並列数に見合う数にした。

**再発防止の運用ルール**: 並列化を謳うスクリプトを実行する前にコードを確認し、
実行を始めたら一定時間後に進捗（rows/files per minute等）を実測して想定と大きく
乖離していないか必ずチェックする（「動いているから待つ」で済ませない）。

## 2026-08-15 12個のコミットを一度もpushしていなかった

**症状**: ローカルでR2移行のコード変更・コミットを済ませ、`npm run deploy`で本番Workerには
反映したが、GitHub Actionsの daily-data-pipeline が本番と異なる（移行前の）古いコードで
動き続け、大量のエラーを出していた。

**原因**: `npm run deploy`はローカルのビルド成果物を直接Cloudflareへアップロードするだけで、
GitHubリポジトリ（`origin`）は更新しない。GitHub Actionsは`origin`上のコードでしか動かない
ため、コミットしただけで満足し`git push`を忘れると、本番Workerとリポジトリ（＝CI）の

**教訓**: 「デプロイした」＝「pushした」ではない。特にCI（GitHub Actions）で動く
スクリプトに変更を入れた場合、`npm run deploy`だけでなく`git push`もセットで行う。
作業の節目でも`git status`（ahead/behindの表示）を確認する。

## 2026-08-15 R2書き込みコスト削減の差分チェックが、Supabaseとの比較で壊れた

**症状**: 継続注目カード（`card_streaks`、価格カテゴリ）が0件になった。トップページの
「価格上昇が続いているカード」欄が表示されなくなった。

**原因**: R2書き込み（無料枠100万件/月）を節約するため、「前日から値が変わったオラクル/
プリントだけをR2へ書く」差分ロジックを`card_current_prices`/`card_print_current_prices`
（Supabase、「今の価格」キャッシュ）との比較で実装していた。しかしこのSupabaseテーブルは
R2への書き込みが成功したかとは無関係に、日次バッチが実行されるたびに無条件で上書きされる。
同じ日にスクリプトを複数回実行した（デバッグ・検証のため）ことで、1回目の実行時点で
Supabase側が「今日の値」に更新され、その後R2側には一度も今日の日付の行が書き込まれない
まま「変化なし」と誤判定され続けた。`compute-card-streaks.mjs`は「最新の行が今日の日付で
なければそのオラクルをストリーク計算から除外する」ため、静かに0件になっていた。

**教訓**: 「Aが成功したかどうか」を、Aと無関係な理由でも更新されうるBの状態で判定しては
いけない。差分書き込みの「前回の値」は、書き込み先（R2）自身から読むか、書き込みと
アトミックに同期する何かでなければ信頼できない。この教訓は上記「gzipSync」の件と対になる：
一方は「並列化したつもりが同期処理が混入」、こちらは「差分チェックしたつもりが
信頼できない比較対象を使っていた」——どちらも"意図通りに動いているつもり"を実際の挙動で
検証しなかったことが共通の原因。

**対応**: Supabaseとの事前比較を削除し、全件をR2側のマージ処理へ渡す。実際に書き込むかどうかの
判定は`mergeCardFile`内で、書き込み先のR2ファイル自体と比較して行う（読み取りは無料枠に
余裕があるため、差分判定のためのGET自体は問題にならない）。

## 2026-08-17 トーナメント履歴バックフィルの並列書き込みでSupabase DBが「ディスク容量不足」に

**症状**: `scripts/backfill-tournaments-from-cache.mjs`（ローカルキャッシュのTopDeck.gg
トーナメント履歴、2.5年分をSupabaseの`tournaments`/`decks`/`deck_cards`へ一括投入する
一回限りのスクリプト）を並列度8→リトライ追加後は並列度4で実行中、
`53100 could not extend file "base/5/17678": No space left on device`エラーが多発。
直後、`mcp__supabase__execute_sql`でのDB接続自体がTLS確立前に切断される状態になった
（管理APIの`get_project_url`は生きていたため、Postgres側だけが不安定化していたとみられる）。
同時期にSupabaseから組織のEgress（データ転送量）超過による猶予期間開始の通知も来ていたが、
これはディスク容量不足とは別の問題（今回のインシデントの原因ではない、混同注意）。

**原因（ダッシュボードで確認済み）**: プロジェクトのコンピュートティアが最小の「Nano」。
ダッシュボードのDatabase Sizeクォータ表示（0.039/0.5GB、8%）は論理的なDB容量枠であり、
Nanoインスタンスに実際に割り当てられている物理ディスク（WAL・一時ソートファイル用）は
それとは別物でずっと小さい。900日分・6フォーマットの並列一括INSERTでWALが急増し、
この小さい物理ディスクを実際に食い潰して`53100 could not extend file`が発生し、
プロジェクト全体（サイト本体含む）が不安定になった。ダッシュボードにも
「Project is exhausting its available disk space」の警告が出ていた。
同時に発生していたEgress超過（6.827/5GB、137%）は無関係な別問題（バックフィル前の
セッション内の大量SELECT/クエリの蓄積によるもの）で、今回のディスク枯渇の直接原因ではない
が、`return=representation`で書き込み行をまるごと返させていた分は無駄なEgress消費だった
ため合わせて`return=minimal`に修正済み。

**教訓**: 「Database Size」（論理容量クォータ）と実際にコンピュートインスタンスへ割り当て
られている物理ディスクは別物で、特にNanoのような最小ティアでは後者がずっとシビア。
大量一括書き込みの前に、テーブルの最終データ量だけでなく実行中に消費するWAL/一時領域の
見積もりと、契約ティアの物理ディスク容量を確認するべきだった。また、並列書き込みで
503が出た時点（1回目の失敗）で「retryを足して継続」ではなく、一旦止めて原因（負荷なのか
容量なのか）を確認すべきだった。

**対応**: バックフィルスクリプトを停止。ユーザーにSupabaseダッシュボードでのEgress/DB容量の
確認を依頼し、実際にEgress超過が原因と判明。再起動しても物理ディスク100%で自己回復不能
だったため、Supabaseサポートへの問い合わせで復旧待ち（対応中、docs参照時点では未解決）。

**再発防止（機械的対策、メモではなくコード）**: このインシデント対応中、同じ晩に
「教訓が既に`docs/incident-log.md`冒頭に明記されていたのに、バックフィルスクリプトを書く前に
読んでいなかった」ことが判明した（8/15にも同様の「教訓を参照しなかった」再発があった）。
「気をつける」だけでは機能しないことは8/15の教訓で既に分かっていたため、今回もコード側に
ガードを追加した: `scripts/lib/supabaseRest.mjs`を新設し、Supabase REST APIへの読み書きを
行う全スクリプト共通のクライアントとした。
- `return=minimal`をデフォルトにし、行データが本当に必要な呼び出しだけ明示的に`return=representation`
- 503は指数バックオフで自動リトライ
- プロセス内の累計転送バイト数を計測し、20MBで警告・100MBで強制停止するガードを内蔵
  （「小さいはずが積み重なって大きくなっていた」ことに実行中に機械的に気づける）
今後Supabaseに読み書きする新規スクリプトは、その場でfetchラッパーを書かずこのクライアントを
使うこと。`scripts/import-tournaments.mjs`・`scripts/backfill-tournaments-from-cache.mjs`も
順次このクライアントへ移行する。

## 2026-08-20 新規Supabaseプロジェクトへの一括投入で、即座に容量超過→読み取り専用ロック

**症状**: 旧プロジェクト（上記2026-08-17インシデントで復旧不能と判断）を削除し、新規に
作成したSupabaseプロジェクトへ、ローカルPostgresで再構築したデータ（`pg_dump --data-only`→
`psql`でCOPY）を一括投入したところ、`tournaments`（5,949件）・`decks`（99,888件）が入った
直後、`deck_cards`（9,543,745行）投入中に容量が500MB上限を超え、プロジェクトが自動で
読み取り専用モードに入った（"Your project is currently using 805.56MB of database space,
which exceeds the Free Plan limit of 500MB"というメール通知で発覚）。COPY自体も
`ERROR: cannot execute COPY FROM in a read-only transaction`で失敗し、`card_oracles`/
`cards`/`card_prints`等は0件のまま（先に投入したはずの行も含めロールバックされていた）。

**原因**: 投入する前に、投入予定データのサイズを一度も見積もらなかった。`deck_cards`
9,543,745行は2.5年分の全トーナメント履歴で、これは元々ML学習用にNAS/ローカルへ
ステージングしたものであり、サイト本体が実際に必要とするのは`compute-deck-stats.mjs`
自身の設計（`PERIOD_DAYS_OPTIONS`最大90日）が示す通り**直近90日分だけ**だった。
「深い履歴はNAS/R2側だけに置き、Supabaseは"今の状態"だけを持つ」という、この晩
何時間も前に自分たちで確立した設計方針を、実際に投入する段になって見失っていた。

**教訓**: これは技術的には新しい教訓ではない。2026-08-17に「大量書き込み前に消費リソースを
確認する」「投入するデータの規模を見積もる」という教訓を得て`docs/incident-log.md`にも
`feedback_check_supabase_capacity_before_bulk_ops`にも記録していたが、数時間後、
文脈が変わった（NAS→ローカル→Supabaseという新しい移行フロー）だけで同じチェックを
またやらなかった。「教訓を覚えているか」ではなく「今やろうとしている具体的な操作に
その教訓を毎回あてはめる習慣が無い」ことが本当の問題だと再確認した。

**対応**: `scripts/check-remote-db-budget.mjs`を新設。投入予定テーブルのローカル合計サイズと
リモートの現在サイズを突き合わせ、予算（デフォルト450MB、Supabase無料枠500MBに安全マージン）を
超える場合は投入前に中断する。今後、Supabase等の容量制限があるリモートDBへ一括投入する
スクリプトは、実行前に必ずこれを通すこと（今回のように「もう教訓は分かっているはず」という
思い込みでチェックを省略しないよう、教訓の記憶ではなくスクリプト自体に強制させる）。
`tournaments`/`decks`/`deck_cards`は直近90日分（`event_date >= 現在 - 90日`）だけに絞って
Supabaseへ再投入し、2.5年分の深い履歴はNAS/ローカルのみに留める。
