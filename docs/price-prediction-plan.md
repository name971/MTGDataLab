# 価格予測モデル 設計メモ

`ml/README.md`から参照されているが実体が無かったため新規作成。`ml/`配下の実装
（`fetch_data.py`・`features.py`・`train_baseline.py`）と、今日（2026-08-15/16）の
R2移行でデータ量が大きく変わった状況を踏まえて設計を整理する。

---

## 1. 目的

カード1枚（oracle_id単位）の「1週間後の価格変動率（対数リターン）」を予測し、
将来的にサイト上で「値上がりが期待できるカード」を提示する。まずはベースラインモデルの
精度を検証する実験段階（本番未反映）。

## 2. データ量の前提が変わった

`ml/README.md`・`train_baseline.py`のコメントは「実質20〜90日程度しか無い」前提で
書かれていたが、これは古い。今日時点の実際のデータ量:

- **R2の価格履歴（`price-history/`月次バルク・`oracle-history/`カード単位）**:
  2024-02-08〜現在まで**約2.5年分、日次**（TCGCSVバックフィル＋日次実データ、
  使用不可プリント除外済み・欠測はnull、`docs/spec.md`4章参照）
- **`card_usage_stats`（採用率）**: 直近60日分のみ保持（Supabase側で自動削除、
  `docs/spec.md`4章）。学習用に長期保存したい場合は別途アーカイブが必要（8章）
- **静的属性**（レアリティ・タイプ・CMC等）: 現在値のみ（過去のレアリティ変更等は
  追跡していない。実務上ほぼ影響しない前提で妥協）

**対応が必要な変更**:
- `train_baseline.py`の`_pick_window_days`は「180日以上あれば train:test=8:1」という
  最上位の分岐しか実質使われなくなる。180日未満に縮小するロジックはもう当面使われない
  （データが既に2.5年分ある）ため、指示書想定に近い訓練/テスト窓（例: 2年訓練/3ヶ月
  テスト、ウォークフォワードで数フォールド）にそのまま設定してよい
- **`ml/fetch_data.py`のD1依存はもう不要、要修正**: `fetch_own_price_history()`が
  Cloudflare D1の`price_history_archive`（「自前の実データ、最も信頼できるソース」
  という位置づけ）を取得し、R2（`fetch_r2_price_history()`）は「D1に無い日付だけ
  補完」という優先順位で実装されている。しかしこのD1テーブルは2026-08-15のR2全面
  移行で**完全に書き込みが止まっている**（`docs/spec.md`4章・`docs/incident-log.md`
  参照）。今のR2側は日次の実データも含めて2024-02〜今日まで単独で連続した履歴を
  持っているため、D1経由のロジックはもう不要。`fetch_r2_price_history()`だけで
  完結するように簡略化してよい（D1_DATABASE_ID・fetch_own_price_history関連のコードは
  削除対象）
- 上記の理由により、**キャッシュ済み`ml/data/*.parquet`（8/14時点）は作り直しが必須**。
  今日のR2側の使用不可プリント除外修正・全面書き換えより前のデータのため、そのまま
  使うと汚染されたデータで学習することになる

## 3. 特徴量（現状）

`ml/features.py`に実装済み:

| カテゴリ | 特徴量 | 備考 |
|---|---|---|
| 価格系列 | `return_1d`/`return_7d`/`return_30d`、`ma_7d`/`ma_30d`、`price_vs_ma7d`、`volatility_7d` | 全て過去方向のshift/rolling、未来参照無し（データリーク対策） |
| 採用率 | `usage_rate_max`（フォーマット横断最大）、`usage_rate_change` | v1はフォーマット別の内訳を持たない |
| 静的属性 | `rarity_num`、`cmc`、`is_reserved`、`is_serialized`、タイプ別フラグ | 現在値のみ |

先行研究（Pawlicki et al., CS229 2014）では採用率の3日差分が単独で最も予測に効いていた
（`src/lib/dbTrendingRanking.ts`のUSAGE_WEIGHT設計でも同じ知見を採用済み）。現状の
`usage_rate_change`は直近1点のみの差分で、複数日（1/3/6日等）の差分は特徴量に
していない。データが十分に溜まった今、ここを厚くする余地がある。

## 4. モデル・評価方法（現状と拡張の方向性）

**現状**: 単一LightGBM（`objective=quantile, alpha=0.5`、点推定相当）、ウォークフォワード
CVでMAE/RMSE/方向的中率を評価。

**将来（データが実際に使えることを確認した後）**:
- CatBoost/Ridge回帰とのスタッキングアンサンブル（`ml/README.md`に既述、未着手）
- 分位点予測（`alpha`を複数設定）による80%予測区間の提示＋簡易バックテスト
- SHAP分析による特徴量重要度の可視化（モデルの説明可能性、将来サイトに載せる場合の
  信頼性材料にもなる）

これらはいずれも「ベースラインの精度が実用に足ると判断できてから」着手する
（`ml/README.md`の既定方針を維持）。

## 5. 本番反映（未着手・要検討）

- 予測結果を書き戻す先: 新規Supabaseテーブル（1オラクル1行、日次更新の「今の価格」
  キャッシュ群と同じ設計思想）を想定。**価格履歴と同じ轍を踏まないよう、時系列で
  予測結果を溜め込む設計にはしない**（`card_current_prices`と同様、最新の予測値だけを
  1行で持つ）
- 表示単位: 「予測変化率±X% / N%の確信度」のような形。`train_baseline.py`の
  `print_top_movers`が既に近い出力（Top10予測変化率）を作っているので、これを
  Supabase書き込みに置き換えれば動く見込み
- 実行頻度: 日次バッチに組み込む場合、LightGBMの学習自体は数秒〜数十秒で終わる規模
  想定なので、既存の`daily-data-pipeline.yml`に追加するステップとして無理はない
  （Python実行環境は既に`ml/fetch_tcgcsv_history.py`等で使っていたが、2026-08-15の
  変更で日次パイプラインからPythonステップは一旦無くなっている。再度追加する場合は
  `actions/setup-python`のステップを復活させる必要がある）

## 6. 次のステップ（優先順）

1. `ml/fetch_data.py`からD1（`fetch_own_price_history`）依存を削除し、R2単独で
   完結するように簡略化する
2. 簡略化した`ml/fetch_data.py`を再実行し、`ml/data/*.parquet`を作り直す
   （2.5年分、使用不可プリント除外済みの最新データで）
3. `train_baseline.py`のウォークフォワード窓を、実際に使えるようになった長期データに
   合わせて調整する（`_pick_window_days`の縮小ロジックが不要になっている前提を検証）
4. ベースラインの精度（MAE/RMSE/方向的中率）を実データで確認し、実用に足るか判断する
5. 実用に足ると判断できたら、5章の本番反映を検討する

## 未解決の論点

- 採用率（`card_usage_stats`）は60日しか保持していないため、学習に使える採用率の
  履歴は価格ほど長くない。学習期間を価格の2.5年に合わせて拡張したい場合、採用率側の
  長期アーカイブも別途必要になる（今は無い）
- デッキ未使用カード（カタログ、D1由来）を予測対象に含めるか。今の`fetch_data.py`は
  Postgres中心（追跡カード）を前提にしている可能性が高く、要確認
