# 価格予測モデル 設計メモ

`ml/README.md`から参照されているが実体が無かったため新規作成。`ml/`配下の実装
（`fetch_data.py`・`features.py`・`train_baseline.py`）と、今日（2026-08-15/16）の
R2移行でデータ量が大きく変わった状況を踏まえて設計を整理する。

---

## 1. 目的

カード1枚（oracle_id単位）の「1週間後の価格変動率（対数リターン）」を予測し、
将来的にサイト上で「値上がりが期待できるカード」を提示する。まずはベースラインモデルの
精度を検証する実験段階（本番未反映）。

## 2. データ量の前提が変わった

`ml/README.md`・`train_baseline.py`のコメントは「実質20〜90日程度しか無い」前提で
書かれていたが、これは古い。今日時点の実際のデータ量:

- **R2の価格履歴（`price-history/`月次バルク・`oracle-history/`カード単位）**:
  2024-02-08〜現在まで**約2.5年分、日次**（TCGCSVバックフィル＋日次実データ、
  使用不可プリント除外済み・欠測はnull、`docs/spec.md`4章参照）
- **`card_usage_stats`（採用率）**: 直近60日分のみ保持（Supabase側で自動削除、
  `docs/spec.md`4章）。学習用に長期保存したい場合は別途アーカイブが必要（8章）
- **静的属性**（レアリティ・タイプ・CMC等）: 現在値のみ（過去のレアリティ変更等は
  追跡していない。実務上ほぼ影響しない前提で妥協）

**対応が必要な変更**:
- `train_baseline.py`の`_pick_window_days`は「180日以上あれば train:test=8:1」という
  最上位の分岐しか実質使われなくなる。180日未満に縮小するロジックはもう当面使われない
  （データが既に2.5年分ある）ため、指示書想定に近い訓練/テスト窓（例: 2年訓練/3ヶ月
  テスト、ウォークフォワードで数フォールド）にそのまま設定してよい
- **`ml/fetch_data.py`のD1依存はもう不要、要修正**: `fetch_own_price_history()`が
  Cloudflare D1の`price_history_archive`（「自前の実データ、最も信頼できるソース」
  という位置づけ）を取得し、R2（`fetch_r2_price_history()`）は「D1に無い日付だけ
  補完」という優先順位で実装されている。しかしこのD1テーブルは2026-08-15のR2全面
  移行で**完全に書き込みが止まっている**（`docs/spec.md`4章・`docs/incident-log.md`
  参照）。今のR2側は日次の実データも含めて2024-02〜今日まで単独で連続した履歴を
  持っているため、D1経由のロジックはもう不要。`fetch_r2_price_history()`だけで
  完結するように簡略化してよい（D1_DATABASE_ID・fetch_own_price_history関連のコードは
  削除対象）
- 上記の理由により、**キャッシュ済み`ml/data/*.parquet`（8/14時点）は作り直しが必須**。
  今日のR2側の使用不可プリント除外修正・全面書き換えより前のデータのため、そのまま
  使うと汚染されたデータで学習することになる

## 3. 特徴量（現状）

`ml/features.py`に実装済み:

| カテゴリ | 特徴量 | 備考 |
|---|---|---|
| 価格系列 | `return_1d`/`return_7d`/`return_30d`、`ma_7d`/`ma_30d`、`price_vs_ma7d`、`volatility_7d` | 全て過去方向のshift/rolling、未来参照無し（データリーク対策） |
| 採用率 | `usage_rate_max`（列名は旧称のまま、中身は`deck_sample_size`加重のフォーマット横断プール比率）、`usage_rate_change_{1,3,6}d` | 2026-08-16に集計方法をPawlicki et al.に合わせて変更済み |
| 静的属性 | `rarity_num`、`cmc`、`is_reserved`、`is_serialized`、タイプ別フラグ | 現在値のみ |

先行研究（Pawlicki et al., CS229 2014）の採用率は「直近7日で使われた回数／同期間に
使われた全カードの回数」で、特定フォーマットに絞らず全デッキをプールした比率。
これに合わせ、v1の「一番使われているフォーマットでの採用率（max）」から、
`deck_sample_size`（フォーマットごとの集計デッキ数）を重みにした加重平均へ変更した
（`ml/features.py`の`build_usage_features`。raw使用回数は`card_usage_stats`に残って
いないため、`usage_rate × deck_sample_size`を近似的な使用回数として扱っている）。
また採用率の3日差分が単独で最も予測に効いていたという知見を踏まえ、1日前比だけでなく
3日・6日前比も特徴量に追加済み（`usage_rate_change_{1,3,6}d`）。

**検証結果（2026-08-16、集計方法変更後の再学習）**: MAE=0.0295、RMSE=0.1037、
方向的中率=54.5%と、変更前から数値上ほぼ変化無し。前節で判明した通り、候補カード
（再録禁止/シリアル/高額）の0.7%しか採用率データを持たないため、集計方法をどう
変えてもこの候補集団には採用率特徴量自体がほぼ存在せず、影響が出なかったと考えられる。
的中率を上げたいなら、採用率の集計方法よりも候補カードの絞り込み条件か
価格モメンタム系特徴量の強化を優先すべき。

**追記（2026-08-16）**: 上記の「0.7%」はさらに検証したところ、行ベースでは正しいが
「候補カードの大半が未採用」という意味ではなかった。原因は`card_usage_stats`が
Supabase側で直近60日分しか保持しない設計（`docs/spec.md`参照）で、価格データの期間
（約2.5年）に対して採用率データが直近23日分しか無いこと。ユニークカード単位で見ると
候補カード1,891種のうち413種（約22%）は直近23日間のどこかで採用実績があり、
「大半が本来無関係」という解釈は誤りだった。

Pawlicki et al.は採用率が無いサンプルをデータセットから除外する方式だったが、
このプロジェクトでは大半の行が該当し除外は非現実的（学習データが99%失われる）。
そのため`ml/features.py`の`fillna(0)`（「データ無し」を「0%＝未採用」として埋めていた）
を撤廃し、NaNのままLightGBMのネイティブな欠損値対応に委ねる方式に変更した。
再学習の結果、全体平均は54.5%で変化しなかったが、フォールド別では2025-08〜10月が
56.3%、2026-02〜04月が59.0%など、個別フォールドで改善が見られた
（採用率データが実質存在しない直近2フォールドはほぼ変化なし）。

根本対応（`card_usage_stats`の長期アーカイブ）は未着手のまま。過去データは
60日ロールオフで既に失われているため取り戻せないが、今後の日次バッチにR2への
差分書き込みステップを足せば、これから先の期間については長期保持できる。

### 自動化パイプラインの実行可能性チェック（2026-08-16）

**現状、日次バッチだけではモデル学習できない**ことが判明。今日ローカルで構築した
採用率アーカイブ（`usage_stats.parquet`/`win_rate_history.parquet`/
`sideboard_usage_stats.parquet`、いずれもTopDeck.gg APIから取得した
`tournament_usage_history.ndjson`が元）はどこにもクラウド保存しておらず、
GitHub Actionsのランナー（毎回まっさらな環境）では再現できない
（`price_history.parquet`等それ以外のデータはR2/Supabase/D1/Scryfallバルクから
再構築可能）。

**対応**: 価格アーカイブと同じパターンで、採用率アーカイブもR2に永続化する必要が
ある。日次バッチでは直近数日分だけTopDeckから差分取得してR2側にマージする
（`mergeCardFile`と同じ発想）。サイト側の高速参照は不要（ML学習専用データのため）
なので、価格アーカイブで使った「カード単位ファイル」層は不要——月次バルク
ファイルだけで十分、書き込み爆発問題を最初から回避できる設計にする。

**コスト試算**: 生データ9,531,959行・約1.4GB（未圧縮）。gzip圧縮で約150〜180MB
（R2無料枠10GBの2%未満）。月次バルク方式なら書き込みは月間30〜31件程度、
読み込みは日次フル再学習でも月間900回程度——価格アーカイブ（2.5年・全カード・
日次）よりデータ規模が2桁小さいため、コスト面は問題にならない見込み。

- 実行頻度: 日次でシンプルにする（週次/日次分離はまず不要。モデル学習自体は
  「全期間で1回学習」するだけなら数分程度で終わる規模。既存の`daily-data-pipeline.yml`
  に追加するステップとして無理はない想定だが実測は未検証）。Python実行環境は
  既に`ml/fetch_tcgcsv_history.py`等で使っていたが、2026-08-15の変更で日次
  パイプラインからPythonステップは一旦無くなっている。再度追加する場合は
  `actions/setup-python`のステップを復活させる必要がある

### ベースライン評価結果（2026-08-16、実データ906日分）

6フォールド（2025-08〜2026-08）のウォークフォワード平均:

| 指標 | 値 |
|---|---|
| MAE | 0.0295 |
| RMSE | 0.1037 |
| 方向的中率 | 54.5% |

方向的中率54.5%はコイントス（50%）よりわずかに高い程度で、「わずかに予測力は
あるが強くはない」という結果。このまま本番反映するにはまだ弱い。3章で挙げた
特徴量の拡充（採用率の複数日差分等）やモデルの改善（スタッキング等）でどこまで
伸びるかを見てから、本番反映を判断するのが妥当。

**訂正（2026-08-16、論文全文を読んで判明）**: 以前ここに「先行研究（Pawlicki et al.）
と同程度の水準」と書いていたが、論文の全文（PDF）を読めていない段階での憶測で、
不正確だった。論文の実測値は分類誤差e=11%（テストセット、ロジスティック回帰、
ラベル3=$0.50マージン付き二値分類）で、これは「7日後の価格変動の符号をマージン
無しで予測する」このプロジェクトの方向的中率54.5%とは、タスク設計（マージン付き
二値分類 vs マージン無し回帰の符号一致率）も評価方法も異なり、単純比較できない。
今のところ論文と直接比較可能な指標は無い。比較したい場合は同じラベル3方式
（続く行に既存の記述あり、以下は候補カード絞り込みの見直しに関する追記）

**候補カードの絞り込みを再設計（2026-08-16）**: 旧絞り込み（再録禁止/シリアル/
3000円以上）は「高額カード」を機械的に集めていたが、これは競技需要と無関係な
コレクター動機のカードばかりで、採用率特徴量がほぼ死んでいた根本原因だった
（0.7%問題、上記参照）。MTGプレイヤーは大別すると競技勢（トーナメントで使う
非Foil最安値のカードを買う。採用率と価格が連動）とコレクター勢（Foil・限定・
希少カードを、採用率と無関係に買う）に分かれるという整理に基づき、候補を
以下の2グループの和集合に変更した（`ml/features.py`の`build_training_frame`）:
  - 競技勢: `card_usage_stats`に一度でも登場した（＝トーナメントで使われた
    実績がある）オラクル。価格は既存の`jpy_est`（非Foil最安、
    `compute-cheapest-price-snapshots.mjs`参照）をそのまま使う
  - コレクター勢: 再録禁止 or シリアル番号入り（価格の絶対額は判定基準から除外。
    競技・コレクターどちらの動機とも直結しないため）

この結果、候補が1,891オラクル/853,627行→10,720オラクル/8,523,791行に拡大。
ただし下限価格を設けなかった初回試行ではMAEが0.0295→0.0802に悪化（数円〜数十円の
バルクカードは僅かな価格変動が%表示だと誇張されノイズになるため）。
`CANDIDATE_MIN_PRICE_JPY = 300`（300円未満を除外）を追加して再学習した結果:

| 指標 | 旧絞り込み | 新絞り込み（下限無し） | 新絞り込み（300円下限） |
|---|---|---|---|
| MAE | 0.0295 | 0.0802 | 0.0529 |
| RMSE | 0.1037 | 0.1457 | 0.1248 |
| 方向的中率 | 54.5% | 55.9% | **56.1%** |

方向的中率は54.5%→56.1%に改善。MAEは旧絞り込みより悪化しているが、対象母集団
自体が大きく広がった（値動きの荒いカードも含む）ためで、母集団が違う数値同士の
単純比較はできない。的中率が主指標として改善した点は、絞り込みの方向性
（採用率と価格が連動する競技勢を軸にする）が正しかったことを裏付けている。

**セグメント別モデルに分離（2026-08-16）**: 競技勢とコレクター勢は価格が動く
理由が正反対（採用率が効く vs 採用率と無関係にFoil/希少性で動く）なので、1つの
LightGBMに混ぜるのをやめ、`ml/features.py`の`build_training_frame(segment)`で
`"competitive"`/`"collector"`別々にデータフレームを組み立て、`train_baseline.py`も
セグメントごとに独立して学習・評価するように変更した。コレクター勢は
`jpy_est_foil`（無ければ`jpy_est`にフォールバック。Foil自体が存在しない古い
再録禁止カードが多いため）を価格系列に使う。競技勢とコレクター勢の両方に該当する
オラクルは競技勢側にのみ含める（重複無し、実装側でassert済み）。

| 指標 | 統合（300円下限） | competitive単独 | collector単独 |
|---|---|---|---|
| MAE | 0.0529 | 0.0565 | **0.0218** |
| RMSE | 0.1248 | 0.1298 | **0.0698** |
| 方向的中率 | 56.1% | **56.4%** | 54.4% |

競技勢: 4,426オラクル/1,899,330行。コレクター勢: 298オラクル/226,983行
（母数がかなり小さい）。コレクター勢はMAE/RMSEが大幅に良い（Foilの価格変動自体が
緩やか）が、的中率は競技勢よりやや低い（採用率のような明確な先行指標が無いため）。
統合モデルの数値は両者の中間に丸め込まれていた形で、分離した方が実態に即した
評価になった。

**`return_3d`特徴量の追加（2026-08-16）**: 論文（Pawlicki et al.）で価格・採用率・
売上のいずれも3日差分が単独で最も予測に効いていたという知見を踏まえ、採用率側
（`usage_rate_change_3d`）だけでなく価格側にも`return_3d`（3日リターン）を追加した。
結果はcompetitive 56.4%→56.3%、collector 54.4%→54.6%とほぼ横ばいで、明確な改善
効果は無し。`return_1d`/`return_7d`と重複度が高く新規情報が少なかったと考えられる。
害は無いため特徴量としては残すが、的中率向上の決め手にはならなかった。

（マージン付き二値分類）をこちらのデータでも作って評価し直す必要がある。

**禁止・再録を特徴量に追加（2026-08-16）**: 「禁止は今後の採用率が0になる強い
シグナル」「再録は価格を下げる」という着想を反映。データはすべてローカル生成
（クラウド課金と無関係）:
  - `ml/build_reprint_history.mjs`: Scryfallバルクデータから、オラクルごとの
    再録日（同日複数バリエーションは1回の再録イベントとして重複除去済み。
    使用不可プリントは`rebuild-catalog-prints.mjs`と同じ判定で除外）を
    `ml/data/reprint_history.ndjson`に書き出す
  - `ml/build_banned_history.mjs`: `src/lib/bannedCards.ts`（`/banned-cards`
    ページ用の手動キュレーションリスト）から「禁止」のみ（「制限」は1枚まで
    使えるため採用率が0にならないので対象外）を抽出し、カード名をoracle_idに
    解決して`ml/data/banned_history.ndjson`に書き出す
  - `ml/features.py`に`build_reprint_features`（`reprint_count`＝累計再録回数
    〈初版除く〉、`days_since_last_reprint`＝直近再録からの経過日数、
    `pd.merge_asof`で点時点計算・データリーク無し）と`build_banned_feature`
    （`is_banned`＝追跡対象フォーマットのいずれかで禁止済みか）を追加

| 指標 | 追加前 | 追加後 |
|---|---|---|
| competitive 的中率 | 56.3% | **56.6%** |
| collector 的中率 | 54.6% | **55.0%** |

両セグメントで小幅改善。特徴量重要度を見ると`days_since_last_reprint`が
competitiveセグメントで**全28特徴量中1位**（価格モメンタム系を上回る）、

## 7. 分類タスクへの再定義（不均衡データ対策、2026-08-16）

先行研究の再調査で、Shishido & Niimi (2023)
"Prediction Soaring Price by Decision Tree Dealing with Imbalanced Data in
Trading Card Game Market"（International Journal of Digital Society）を発見。
MTG中古市場の価格急騰予測を決定木で二値分類した研究で、**不均衡データ対策を
何もしないとRecall（急騰カードを実際に当てられた割合）が0付近まで落ち込む**
（Accuracy自体は98%と高く見えるが、大半のカードを機械的に「急騰しない」と
予測しているだけ）ことを示し、undersampling/cost-aware（コスト考慮型学習）で
Recallを大幅に改善できたと報告している。

今までの回帰＋方向的中率という評価軸は、圧倒的多数を占める「ほとんど動かない
カード」に引っ張られやすく、本来知りたい「大きく値上がりするカードを当てる」力を
直接測れていなかった可能性がある。この着想を検証するため、`ml/train_classification.py`
を新規作成し、予測を「7日後に急騰するか/しないか」の二値分類として再定義した:

  - 急騰の定義: 各フォールドの**訓練データの分布からのみ**動的に閾値を決める
    （上位`SOAR_QUANTILE=0.90`パーセンタイル。セグメントで値動きのスケールが
    大きく違う上、期間ごとに市場全体のボラティリティも変わるため、固定%閾値や
    テストデータを覗いた閾値は使わない）
  - モデル: LightGBM分類器。「対策無し」と、論文が最も汎用的と結論付けていた
    cost-aware相当（`class_weight="balanced"`）を比較
  - 評価: Precision/Recall/F1（Accuracyは不均衡データでは意味を持たないため使わない）

### 結果

| セグメント | 指標 | 対策無し | cost-aware |
|---|---|---|---|
| competitive | Precision | 0.492 | 0.208 |
| competitive | Recall | 0.020 | **0.725** |
| competitive | F1 | 0.039 | **0.322**（8倍） |
| collector | Precision | 0.292 | 0.178 |
| collector | Recall | 0.048 | **0.412** |
| collector | F1 | 0.079 | **0.243**（3倍） |

論文と同じパターンが完全に再現された。対策無しはほぼ全カードを「急騰しない」と
予測してRecallが2〜5%しかない（見かけ上Precisionは高いが実用性が無い）一方、
`class_weight="balanced"`にするとRecallが41〜73%まで跳ね上がった。

実用的な意味: competitiveの閾値（上位10%、+7%前後）に対してPrecision 0.208は、
ランダムに選ぶ場合のベースレート（10%）の約2倍の的中率で、実際に急騰する
カードの73%を拾えている。「見逃さず候補に挙げるスクリーニング」用途としては
実用に足る水準。これまで試した個別特徴量追加・スタッキングよりも明確に効果の
大きい、タスク設計レベルの改善だった。

### 急騰の閾値（SOAR_QUANTILE）の比較

F1に絶対的な「合格ライン」は無く、分野や母数の偏り具合に強く依存するため、
比較には**ランダム予測との比**（母数の偏り＝base_rateでランダムに正例予測すると
Precision≈Recall≈F1≈base_rateになる）を使うのが妥当。上位30%/20%/10%で比較した
（いずれも`class_weight="balanced"`）:

| 定義 | 閾値目安 | F1（生の値） | ランダム基準 | 倍率 |
|---|---|---|---|---|
| competitive 上位30% | +2.0% | 0.508 | 0.300 | 1.69倍 |
| competitive 上位20% | +3.7% | 0.437 | 0.200 | 2.19倍 |
| competitive 上位10%（採用） | +7.2% | 0.322 | 0.100 | **3.22倍** |
| collector 上位30% | +0.9% | 0.392 | 0.300 | 1.31倍 |
| collector 上位20% | +1.4% | 0.318 | 0.200 | 1.59倍 |
| collector 上位10%（採用） | +2.4% | 0.243 | 0.100 | **2.43倍** |

F1の生の値だけを見ると閾値を緩めた（上位30%）方が良く見えるが、これは
「当てやすい問題に閾値を下げているだけ」という側面がある。ランダム基準との倍率
で見ると逆転し、**閾値を厳しく保つ（上位10%）方がモデルの相対的な予測力は強い**。
「本当に大きく値上がりするカードを見つけたい」という当初の目的にも合致するため、
`SOAR_QUANTILE=0.90`（デフォルト値）を採用とする。

### 固定%閾値（当初の想定「7日後に+X%以上」）でも検証

上記はパーセンタイル方式（訓練データの分布に対する相対閾値）での検証だったが、
当初の想定通り固定の絶対%閾値でも別途検証した（`train_and_evaluate_fold`に
`fixed_threshold_pct`引数を追加、`class_weight="balanced"`固定）:

| セグメント | 閾値 | Precision | Recall | F1 | base_rate | 倍率 |
|---|---|---|---|---|---|---|
| competitive | +5%以上 | 0.268 | 0.716 | 0.389 | 16.0% | 2.43倍 |
| competitive | +10%以上 | 0.154 | 0.738 | 0.254 | 6.4% | 3.99倍 |
| competitive | +15%以上 | 0.100 | 0.744 | 0.176 | 3.1% | 5.67倍 |
| competitive | +20%以上 | 0.070 | 0.737 | 0.128 | 1.7% | **7.42倍** |
| collector | +5%以上 | 0.112 | 0.301 | 0.162 | 3.7% | 4.38倍 |
| collector | +10%以上 | 0.064 | 0.140 | 0.086 | 1.2% | 6.95倍 |
| collector | +15%/+20%以上 | - | - | - | 0.4〜0.7% | 参考値（サンプル数不足で不安定） |

competitiveでは、Recallが72〜74%でほぼ一定を保ったまま、閾値を厳しくするほど
ランダム予測との倍率が伸びていく（2.43倍→7.42倍）。「本当に大きく値上がりする
カードほど、モデルにとって見分けやすいシグナルが存在する」ことを示しており、
パーセンタイル方式の結果（閾値を厳しく保つほど相対的な予測力が強い）と整合する
裏付けになった。collectorは+15%以上になるとbase_rateが1%未満まで下がり、
テストフォールドあたりの陽性サンプルが数十件程度しかないため数値が不安定
（参考程度）。

### 急落の対称性検証

急騰だけでなく急落（`direction="down"`パラメータを追加）も同じ枠組みで検証した。

| セグメント | 方向 | Precision | Recall | F1 | 倍率 |
|---|---|---|---|---|---|
| competitive | 急騰 | 0.208 | 0.725 | 0.322 | 3.08倍 |
| competitive | 急落 | 0.206 | 0.677 | 0.314 | 3.63倍 |
| collector | 急騰 | 0.178 | 0.412 | 0.243 | 2.38倍 |
| collector | 急落 | 0.123 | 0.299 | 0.170 | 2.27倍 |

急騰・急落はほぼ対称的な精度で予測できることを確認。

### 分類モデルでの特徴量重要度の再検証

回帰では重要度が0だった特徴量（採用率・勝率・投入枚数・サイドボード・カテゴリ
フラグ等、collectorセグメントで16位以降が軒並み0だった件）が、分類タスクに
変えても復活するかを検証した。

  - **competitive**: `usage_rate_max`が9位、`win_rate_avg_7d`が16位と、回帰時と
    ほぼ同順位のまま。`days_since_release`/`days_since_last_reprint`が2位・3位に
    上昇（分類だとさらに強調される）
  - **collector**: 回帰で重要度0だった16特徴量は、分類タスクに変えても**全て
    重要度0のまま**。データの問題（そもそもcollectorカードにトーナメント関連の
    情報がほぼ存在しない）であって、タスク設計（回帰 vs 分類）の問題ではないことが
    確定した

### 確率上位N件ランキング方式（実用上、最も有望な結果）

固定閾値での0/1判定（`predict()`、確率0.5が境目）ではなく、分類確率が高い順に
トップN件だけを見る「確信度ランキング」方式（`evaluate_top_n`関数、以前の
分位点回帰の確信度フィルターと同じ発想）を検証した。理由: 固定閾値だと
1テスト期間（60日）あたり数百〜千件超のアラートが出てしまい実用的な
「今日チェックすべき候補リスト」にならないことが判明したため（例:
competitive +5%以上閾値で1日あたり約1,370件のアラート）。

| セグメント | 方向 | Top10 | Top20 | Top50 | Top100 |
|---|---|---|---|---|---|
| competitive | 急騰 | 76.7% | 70.0% | 63.0% | 58.2% |
| competitive | 急落 | **100%** | 96.7% | 97.3% | 94.7% |
| collector | 急騰 | 45.0% | 44.2% | 36.7% | 34.5% |
| collector | 急落 | 11.7% | 13.3% | 17.7% | 17.8% |

固定閾値の二値分類（Precision 0.15〜0.27程度）と比べて**3〜4倍の精度**。
competitiveの急落予測はTop10でPrecision 100%という結果で、`is_banned`/
競技勢の急落がなぜここまで高精度か実際に中身を検証したところ（後述）、
`is_banned`/`days_since_ban`が理由ではないことが判明した。一方collectorの
急落はTop10で11.7%と弱く、非対称な結果だった（collectorは上昇の方が下落より
予測しやすい）。

実用上、これまで検証した中で最も有望な設計。サイトに「今日の注目候補」を
出すなら、固定閾値の二値分類よりこの確信度ランキング方式を使うべき。

**急落Top30が高精度（97.2%）な理由を実データで検証（2026-08-16）**: ユーザーが
「全部禁止カードなのでは」と疑問視したため、実際にTop30の中身を確認した。

  - `is_banned=1`: 0/30件、直近再録（`days_since_last_reprint<=14`）: 0/30件
    ——禁止改定・再録が理由ではなかった
  - 特徴量重要度でも`is_banned`/`days_since_ban`はトップ10圏外（1位は
    `days_since_release`、2位`days_since_last_reprint`だが、これらもTop30の
    実際の値はNaN＝再録履歴が無いカードだった）
  - 実際の中身: Top30の`return_1d`は-6%〜-29%、`return_7d`は-20%〜-50%と、
    **予測時点で既に急落が進行中**のカードだった。`set_avg_return_7d`も
    -13%〜-40%と同じセットの他カードも軒並み暴落しており、セット全体の
    暴落イベントに巻き込まれている状況
  - 結論: このモデルがやっているのは「静かな状態から暴落を予知する」ことではなく
    **「既に急落し始めているカードが、その後も下がり続けることを見抜く」
    モメンタム継続の予測**。これは「まだ何も起きていない状態から予測する」より
    本質的に簡単な問題であり、それが高精度の理由。実用上は「下げ止まらなさそう
    だから今は買うな」という判断材料として価値があるが、「誰も気づいていない
    暴落の予兆を検知している」わけではない点は利用時に明記すべき注記

**次のアクション候補**: この分類ベースのアプローチ（特に確信度ランキング方式）を
本採用するかの判断（`train_baseline.py`の回帰と併用するか置き換えるか）、
本番反映（5章）の設計にこの方式を組み込む検討。急落予測を表示する場合は
「モメンタム継続の検知」である旨をUI上の説明に含める。

### collectorセグメントの実用化は見送り（2026-08-16）

competitive（Top10急騰76.7%・急落100%）とcollector（Top10急騰45.0%・急落11.7%、
母数298オラクルと小さい上にトーナメント関連特徴量が軒並み重要度0）の精度差が
大きいため、**本番反映はcompetitiveのみを対象とする**方針にした。collectorは
今回のデータソース（トーナメント結果・価格履歴・Scryfallメタデータ）だけでは
天井が見えている——コレクター需要は見た目の人気・ノスタルジー・SNS話題性・
グレーディング申請動向など、ゲーム内データでは説明できない要因に左右されやすい
ため。

先行研究（Pawlicki et al. 2014、Shishido & Niimi 2023）もいずれもトーナメント
環境で使われるカードが主対象で、コレクター需要主導の値動き予測はほぼ手つかずの
領域であり、新規性はある。ただし伸ばすには質的に異なるデータ（eBay等の落札価格・
出品数、PSA/BGSのグレーディング申請枚数推移、SNS言及数等）が必要で、今は
無料で入手できるソースが無い（取引量が入手できない問題と同じ壁）。今回は
研究テーマとして記録するに留め、深追いはしない。

## 8. 値上がり幅の段階表示（磁ラダー方式、2026-08-16）

ユーザー指摘: 「上がるかどうか」だけでなく「どれくらい上がるか」も知りたいはず。
`ml/predict_magnitude_ladder.py`を新規作成し、複数の固定閾値（+5%/+10%/+15%/+20%）
それぞれで別々のLightGBM分類器（`class_weight="balanced"`、cost-aware設計）を学習し、
「P(+5%以上)=58%、P(+10%以上)=53%、P(+15%以上)=47%、P(+20%以上)=34%」のように
段階的な確信度を出す設計にした。

**発覚した問題と修正**: 素朴に各閾値の確率を並べると、閾値が厳しいモデルほど
`class_weight="balanced"`の重み付けが強くなる（少数派の重みが母数の逆数に比例して
増える）ため、出力される「確率」が閾値と体系的に逆相関してしまい、
「+20%以上の確率(96%) > +5%以上の確率(89%)」という矛盾が実際に発生した。

  1. 各閾値モデルに`CalibratedClassifierCV`（`method="isotonic"`、`cv=3`で内部
     ホールドアウトを切って確率を実測ベースに校正）を被せることでほぼ解消
     （単調性違反 100%近く → 3.5%）
  2. 残った3.5%の違反は、閾値の緩い方から順に`np.minimum`で押さえ込む後処理
     （`predict_ladder`関数）で完全に解消（違反0件を確認）

この設計はcompetitiveセグメント向けに実装・検証済み（collectorは上記の通り実用化
見送りのため対象外）。まだ`train_baseline.py`/`train_classification.py`の
本流パイプラインには統合していない、検証用スクリプトの段階。

**表示文言の方針（2026-08-16、ユーザー指摘）**: 「予測変化率+10%」のような単一の
数値表記は「10%ぴったり上がる」という誤読を招きやすい。モデル自体が「N%以上上がる
確率」という二値分類として学習・キャリブレーションされているため、表記も
「+10%**以上**値上がりする確率: 53%」のように「以上」を明記し、複数閾値を並べて
段階的に見せる（例: +5%以上58% / +10%以上53% / +15%以上47% / +20%以上34%）。
本番反映時のUI文言はこの方針に合わせる。

**高額カードが%ランキングで埋もれる懸念を検証（2026-08-16）**: ユーザー指摘
「%ベースだと高額カードが埋もれやすいのでは」を実データで検証した。

| 価格帯 | 候補全体での割合 | 確率Top30での割合 |
|---|---|---|
| 3,000円以上 | 12.5% | 23.3%（7/30、むしろ過剰代表） |
| 5,000円以上 | 7.0% | 6.7%（2/30、ほぼ同程度） |
| 1万円以上 | 3.0% | 0%（0/30） |

3,000円・5,000円クラスは埋もれておらず候補全体と同程度かそれ以上の比率で
Top30に入っていた。埋もれているのは「1万円を超える極端な高額カード」だけで、
この層は候補全体でも3%しかなく、Top30（全体の0.014%）に統計的に出現しなくても
不自然ではない。期待値（円換算）ベースへのランキング再設計までは行わず、
高額カード向けの価格帯フィルター（例:「1万円以上のみ表示」トグル）を用意する
方向で対応する。

### キャリブレーション精度の検証（ウォークフォワード、2026-08-16）

「最新日のトップ10を見た目で確認」しただけでは精度が分からないため、6フォールド
全体で予測確率と実測の的中率を突き合わせて検証した（Brierスコア＝予測確率と
実測の二乗誤差、低いほど良い。予測確率を5分位に分けて`pred_mean`（予測確率の
平均）と`actual_rate`（そのグループの実際の的中率）を比較）。

| 閾値 | Brierスコア | 予測確率 vs 実際の的中率（最高ビン） |
|---|---|---|
| +5% | 0.1217 | 33.8% vs 33.6% |
| +10% | 0.0541 | 18.5% vs 18.8% |
| +15% | 0.0277 | 10.4% vs 10.9% |
| +20% | 0.0158 | 6.2% vs 6.6% |

全閾値・全ビンで予測確率と実際の的中率がほぼ一致（誤差1%未満がほとんど）。
「モデルが+10%以上と言ったら、実際にそのグループの約10%が本当に+10%以上
上がっている」という意味で、段階表示の数字は信頼できることを確認した。

## 9. `days_until_rotation`（Standardローテーション残り日数）を追加（2026-08-16）

Pawlicki et al. (2014)の特徴量27番「Days until card loses tournament legality」
着想。`ml/build_standard_rotation.mjs`がScryfallバルクデータの`legalities.standard`
から、オラクルごとに「現在Standard合法な最も古いプリントの発売日+3年
（`ROTATION_YEARS`、現行ルールの近似値）」をローテーション予定日として算出し、
`ml/features.py`の`build_standard_rotation_feature`が日次の残り日数に変換する。

**実装前の疎密チェック**: competitive候補（6,285オラクル）のうちStandard合法は
1,421件（22.6%）。`is_banned`等（1%未満）よりずっと密度が高く、試す価値ありと
判断した。

**発覚したバグと修正**: オラクル単位でローテーション日を結合しているため、
「現在Standard合法な同じオラクルの、過去の全く別プリント時代の価格行」にまで
現在のローテーション日を当てはめてしまい、`days_until_rotation`の最小値が
-8107日（22年）という異常値が発生した。ローテーション周期を大きく外れる値
（-30日未満 or 3年+うるう年バッファを超える）はNaNにする後処理で修正。

**結果**:

| 指標 | 追加前 | 追加後 |
|---|---|---|
| competitive 的中率 | 57.7% | **57.8%** |
| competitive MAE | 0.0525 | **0.0517** |
| competitive RMSE | 0.1257 | **0.1194**（約5%改善） |
| collector | — | 変化無し（Standard対象カードがほぼ無いため当然） |

重要度は8位/38特徴量。小幅だが今日追加した特徴量の中でも上位クラスの効果。
`days_to_quarter_end`（カレンダーだけの疑似イベント、失敗）とは違い、
ローテーションはゲームルール上実在するイベントであるため、時間的過学習の
再発は無く素直に効いた。

**現状のベースライン（2026-08-16、`days_until_rotation`込み）**: competitive
的中率57.8%・collector的中率54.9%。

## 10. Learning to Rank（LambdaRank）を試行（2026-08-16）

回帰・分類は「7日後の変動率」「閾値を超えるか」という間接的な代理目標を最適化して
いるが、実際にサイトで使うのは「その日の全候補の中でのTop100順位」であるため、
順位そのものを直接最適化する方が実用目的に合っているという仮説（ユーザー指摘）を
検証した。`ml/train_ranking.py`で、日付ごとに「その日の全候補」を1グループとした
LightGBMの`objective="lambdarank"`を実装し、分類ベースの確信度ランキング方式
（8章・9章参照）とPrecision@Nで比較した。

**結果: 理論的な期待に反し、明確に悪化した。**

| N | 分類（cost-aware） | Learning to Rank | 差 |
|---|---|---|---|
| competitive Top10 | 76.7% | 49.0% | -27.7pt |
| competitive Top30 | 69.4% | 43.7% | -25.7pt |
| competitive Top100 | 58.2% | 36.6% | -21.6pt |
| collector Top10 | 45.0% | 23.7% | -21.3pt |
| collector Top100 | 34.5% | 12.1% | -22.4pt |

考えられる理由: `class_weight="balanced"`（cost-aware分類）が不均衡データ
（急騰は少数派）を正しく拾うことに直接効いていたが、LambdaRankのデフォルト設定
にはこの仕組みが無い。LambdaRankは通常NDCG等の指標をチューニングして使うもので、
今回はデフォルトパラメータのまま試したため真の性能を引き出せていない可能性が
ある（`lambdarank_truncation_level`等の調整は未実施）。

**結論**: 「実際の用途に直接最適化する」という理論的な魅力とは裏腹に、そのままの
実装では使い物にならなかった。不均衡データ対策込みの分類ベース確信度ランキング
方式（8〜9章）が引き続き最有力。

**パラメータチューニングを試行（2026-08-16）**: WEB検索でLightGBM LambdaRankの
チューニング指針を調査。`lambdarank_truncation_level`（デフォルト30、NDCG@kの
`k`より少し大きめにするのが定石）を今回の用途（Top100まで見たい）に合わせて
100へ引き上げ、`lambdarank_norm=True`（不均衡データ向けの正規化、デフォルトで
有効なはずだが明示）を設定して再検証した。

| N | 分類（cost-aware） | Rank（デフォルト） | Rank（チューニング後） |
|---|---|---|---|
| competitive Top10 | 76.7% | 49.0% | 49.1%（ほぼ変化無し） |
| competitive Top100 | 58.2% | 36.6% | 38.0%（わずかに改善） |

**結論（確定）**: パラメータ調整では分類ベース方式との差はほとんど埋まらなかった。
分類の`class_weight="balanced"`が損失関数レベルで「少数派（急騰）を正しく拾う」
ことに直接介入するのに対し、LambdaRankにはそれに相当する不均衡データ対策の
仕組みが標準では無いことが根本原因と考えられる。Learning to Rankは不採用とし、
分類ベース確信度ランキング方式（8〜9章）を正式に採用する。

## 11. 訓練期間の長さを検証（2026-08-16）

現行の`train_days=540`（約1年半）が最適か、市場環境の変化（メタ・注目カードの
移り変わり）を考慮すると短い方が良いのではという仮説を検証した。テスト期間は
全設定で同一（直近6区間）に固定し、訓練期間だけを90/180/360/540日で比較した
（competitiveセグメント、確信度ランキング方式のPrecision@N）。

| 訓練期間 | Top10 | Top30 | Top100 |
|---|---|---|---|
| 90日 | 60.0% | 55.0% | 49.2% |
| 180日 | **63.3%** | 57.2% | 54.3% |
| 360日 | 46.7% | 55.0% | 56.5% |
| 540日（現行） | 55.0% | **65.6%** | **57.0%** |

明確な「短い方が良い/長い方が良い」という傾向は見られず、フォールドごとの
ノイズの範囲内と考えられる。Top10だけなら180日が最良だが、本番で使う予定の
Top30・Top100では現行の540日が最も良い結果だった。訓練期間の変更は見送り、
現行設定を維持する。

## 12. モデル自体のチューニング3点セット（2026-08-16）

構造変更（セグメント分離・タスク再定義等）は試したが、既存モデル自体の基本
チューニングは今日一度もやっていなかったため、3つ試した。

### 12-1. ハイパーパラメータのグリッドサーチ

一貫して`n_estimators=200, num_leaves=31, min_child_samples=20`のデフォルトに
近い設定のまま学習していた。competitiveでグリッドサーチした結果、
`n_estimators=500, num_leaves=63, min_child_samples=20, learning_rate=0.05`
（木を増やして深くし、学習率を下げてじっくり学習）が全指標で最良だった:

| 設定 | Top10 | Top30 | Top100 |
|---|---|---|---|
| デフォルト | 63.3% | 58.3% | 53.3% |
| n_estimators=500 | 68.3% | 59.4% | 56.0% |
| num_leaves=63 | 68.3% | 58.3% | 60.2% |
| **n_estimators=500, num_leaves=63, learning_rate=0.05** | **70.0%** | **68.3%** | **61.7%** |

ただし同じ設定をcollector（訓練データ約8.5万行/フォールド、competitiveの約150万行
より2桁少ない）に使うと過学習で逆に悪化した（Top10: 45.0%→33.3%）。
**セグメントごとに別々のハイパーパラメータが必要**と判明し、
`ml/train_classification.py`に`SEGMENT_LGBM_PARAMS`（competitive/collectorで
別設定）を実装、`run_segment`/`train_and_evaluate_fold`/`evaluate_top_n`が
`lgbm_params`引数でオーバーライドできるようにリファクタリングした。

### 12-2. 重要度0の特徴量を削除

collectorで回帰時代から重要度0のままだった16特徴量（採用率・勝率・投入枚数・
サイドボード・カテゴリフラグ等）を除外して比較したが、**ほぼ効果無し**
（Top10: 45.0%→41.7%、Top30: 43.9%→43.3%、Top100: 34.5%→35.2%、誤差レベル）。
LightGBMは木構造のため重要度0の特徴量があっても単に分岐に使われないだけで
実害が少ないと考えられる。不採用。

### 12-3. 複数閾値（SOAR_QUANTILE）アンサンブル

`SOAR_QUANTILE=0.9`単一ではなく、0.85/0.90/0.95の3つの分類器を学習し、
予測確率の平均でランキングする方式を検証した（competitive、チューニング後の
ハイパーパラメータ使用）。

| | Top10 | Top30 | Top100 |
|---|---|---|---|
| 単一（q=0.9のみ） | 70.0% | 68.3% | 61.7% |
| 3閾値（0.85/0.90/0.95）平均 | **73.3%** | 67.2%（-1.1pt） | **66.0%** |

Top10・Top100で改善、Top30のみ僅かに悪化。特に本番で使う予定のTop100で
+4.3ptの改善は意味がある。採用候補。

**まとめ**: 3点のうち2点（ハイパーパラメータ調整・複数閾値アンサンブル）が
実際に効果があった。今日の一連の構造変更（8〜11章）と合わせて、
competitiveのTop100 Precisionは58.2%（9章時点）→66.0%（本日の調整込み）まで
改善した。

### 12-4. SOAR_QUANTILE自体のチューニング

アンサンブルの構成要素（0.85/0.90/0.95）は試したが、単一モデルとして
`SOAR_QUANTILE`自体が0.90で最適かは未検証だった。0.80/0.85/0.90/0.95で
グリッドサーチした結果、**q=0.80（上位20%）が全指標で最良**だった:

| q | Top10 | Top30 | Top100 |
|---|---|---|---|
| **0.80** | **73.3%** | **71.7%** | **66.2%** |
| 0.85 | 70.0% | 68.9% | 65.3% |
| 0.90（旧デフォルト） | 70.0% | 68.3% | 61.7% |
| 0.95 | 60.0% | 58.3% | 51.2% |

閾値を緩めると訓練データの正例が増え、分類器がより自信を持って学習できる
ため。ランダム基準との相対倍率では厳しい閾値の方が高かった（7章参照）が、
実運用で見るのは生のPrecision@Nなので`SOAR_QUANTILE`のデフォルトを0.80に
変更した。

## 13. アーキタイプ単位の相対値動き（サイトの分類器を流用、2026-08-16）

ユーザー指摘: サイトで既に使っている`src/lib/archetypeEngine.ts`
（Badaro/MTGOFormatDataルールベース、`scripts/classify-decks.ts`と同じロジック）を
独自の分類器を作らず流用してほしい。「効果薄そうな気もするけど簡易的に試してみよう」
という位置づけで実装した。

  - `ml/features.py`の`build_archetype_features`: `set_avg_return_7d`と同じ
    leave-one-out設計だが、1枚のカードが複数アーキタイプで使われうる多対多の
    関係を「その日、そのオラクルが最も多く使われていたアーキタイプ」（最頻値）に

|---|---|---|---|

## 15. 今日の取捨選択まとめ（2026-08-16）

一連の検証を踏まえ、何を採用/不採用にするか最終整理した。

**採用済み（`ml/features.py`/`ml/train_classification.py`に反映済み）**:
セグメント分離（competitive/collector）、分類タスクへの再定義
（`class_weight="balanced"`）、`SOAR_QUANTILE=0.80`、セグメント別ハイパー
パラメータ（`SEGMENT_LGBM_PARAMS`）、`set_avg_return_7d`、
`days_since_release`/`days_since_last_reprint`/`reprint_count`、
`days_until_rotation`、`win_rate_avg_7d`/`avg_copies_7d`/サイドボード採用率
（効果は薄いが害も無いため残置）、`archetype_avg_return_7d`（同上）、
確信度トップN方式（実運用の中核設計）、段階表示（`predict_magnitude_ladder.py`）。

**不採用（元に戻し済み）**: Winsorizing、`days_to_quarter_end`、
`momentum_accel`、`is_reserved`×採用率変化の交互作用、3日後予測、
特徴量削減、直近重視の重み付け学習。

**不採用（複数閾値アンサンブル）**: 検証時点（0.85/0.90/0.95の3閾値平均）では
単体q=0.9より良かったが、その後`SOAR_QUANTILE`自体のグリッドサーチで
単体q=0.80がアンサンブルと同等以上（Top10: 同点、Top30: 71.7% vs 67.2%で
単体が上回る）と判明したため、3倍の学習コストをかける価値が無いと判断し不採用。

**検証用スクリプトとして残すが本流には組み込まない**: `train_stacking.py`
（LightGBM+CatBoost+Ridgeスタッキング、効果無し）、`train_ranking.py`
（Learning to Rank、効果無し）。

**不採用（価格帯別モデル、2026-08-21）**: ユーザー仮説「高いカードほど高騰しにくく
暴落しやすい、安いカードほど高騰しやすい」を実データで検証すると部分的に正しかった
（〜300円は上昇>下落、3000-10000円は下落>上昇に逆転）が、主効果は「価格が高いほど
両方向とも動きにくくなる」ことだった。価格帯（〜300円/300-3000円/3000円〜）で
モデルを完全に分けて（同じ急騰/急落閾値、学習器だけ分離）walk-forward検証したところ、
全項目で単一モデル以下（急騰Top10: 73.3%→61.7%、-11.7pt）。学習データが分割される
悪影響が価格帯特有パターンを捉える利点を上回ったと考えられる。`log_price`は既に
単一モデルの特徴量に入っており、価格帯情報自体はある程度活用できていたのも一因。
検証用スクリプトは使い捨てのため削除済み（再現する場合はwalk_forward_folds +
evaluate_top_nベースで作り直す）。

**不採用（新高値/新安値更新フラグ、2026-08-21）**: ユーザー仮説「新安値を更新した
カードはさらに下がりやすいのでは」を実データで検証すると明確に正しかった（新安値
更新後は通常より-5%以下になる確率が15.9%→26.7%に跳ね上がる、新高値更新は特に
シグナルなし）。この相関を`is_new_high`/`is_new_low`（当日以前の全期間の最高値/
最安値を当日が更新したかの2値）として特徴量に追加しwalk-forward検証したところ、
急落Top10で+1.7pt改善した一方、急騰Top30で-6.1pt悪化するなど純減。既存の`log_price`/
`return_*`系特徴量が既にこの情報をある程度含んでいたため、新規特徴量のノイズが
利益を上回ったと考えられる。「実データの相関が本物でも、モデルへの寄与は別問題」
という好例。不採用、featuresから削除済み。

**不採用（株式市場の定番ファクター4種+Foilプレミアム、2026-08-21）**: 「他に株式市場で
効果が知られているのに未着手の特徴量は無いか」という問いから、5つを実データ相関確認→
walk-forward検証の順で試した。

| 特徴量 | 実データでの相関 | モデルへの寄与 |
|---|---|---|
| 52週高値/安値からの乖離率（連続値） | - | 急騰Top10 -3.3pt、Top30/100は+2.8〜+3.2ptと不安定 |
| 短期リバーサル除外モメンタム（return_30d-return_3d） | - | 急騰Top10 -3.3pt、他はほぼ横ばい |
| RSI(14日) | - | 急騰Top10 **-8.3pt**と明確に悪化 |
| クロスセクション順位化（同日内百分位） | - | 全項目±2pt以内、効果なし |
| Foilプレミアム（foil/通常価格比） | 1.2倍未満で-5%以下の確率28.6%（通常は15.9%水準） | **全項目±0.0pt、完全に無効果** |

Foilプレミアムは実データの相関自体ははっきりしていた（新安値更新と同程度）にも関わらず
モデルへの寄与がゼロだった点が興味深い。competitiveセグメントは非Foil最安値を予測対象に
しているため、Foil側の情報が構造的に効きにくいと考えられる。5つとも不採用、
features.pyから削除済み。「実データの相関が本物でも、既存のlog_price/return_*系
特徴量が同じ情報を暗黙に含んでいることが多く、追加特徴量としての伸びしろは小さい」
という、8月の一連の実験（価格帯別モデル・新高値安値フラグ含む）に共通する教訓。
